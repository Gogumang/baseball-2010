# S8 — 수비 AI 상태 8·9·0xe · 메시지 0xbc3 · state[0x19] · 견제 리드 폭 (U-10 ~ U-12)

## 체크리스트

- [x] 1. U-10a: AI 상태 8 (0xb48b6) 세부 — **협살(rundown) 확정**
- [x] 2. U-10b: AI 상태 9 (0xb4838) — **송구 받기 대기 + 송구 타이밍 게이트 확정**
- [x] 3. U-10c: AI 상태 0xe (0xb47da) — **견제 송구 확정** (P2 의 "플레이+0x127" 은 오독)
- [x] 4. U-10d: 메시지 0xbc3 처리처 — **전용 처리기가 없다(확정)**
- [x] 5. U-11: state[0x19] 0.1% 사건 — **동작 확정 / 이름은 "포수 뒤로 빠진 공" 유력**
- [x] 6. U-12: 견제 순간 주자 리드 폭 — **리드 폭은 원본에 없다(확정)**
- [x] 7. 웹판(baseball-2010/src) 대조
- [x] 8. 정정 절

## 요약

U-10·U-11·U-12 를 모두 닫았다. **상태 8 = 협살**(대상 = 다음 루까지 35% 넘게 남은 주자, 기록칸 `P+0x1ec`~`0x1f3`, **수비가 CPU 일 때만**),
**상태 9 = 송구 받기 대기**(루 도착 틱 ≤ 송구 도착 틱이 될 때까지 송구를 미루는 게이트),
**상태 0xe = 견제 송구**(`플레이.vt0x58(state[0x27])`, 견제 때 루 커버는 "루번호+1" 야수로 고정).
**메시지 `0xbc3` 은 처리기가 없다** — 경기 장면 분기표(0x509a0)에서 0xbc3·0xbc4 가 통째로 빠져 기본 반환 `0x523aa` 로 떨어지고,
유일한 실효는 모든 메시지가 먼저 거치는 경기 로직 `vt0xc = 0xafa60`(CPU 송구 결정)을 한 번 돌리는 것이다.
**`state[0x19]`** 는 투구마다 `d_level.dat` 0x2a = 10 / rand(0,10000) → **0.1%**(홈런더비 제외) 로 서는 플래그이고,
서면 볼넷·사구가 아닌 한 `0x3507c` 가 **무작위 각 60~130·세기 160~280** 으로 공을 쏘고 포수를 에러 동작(+0xb8=6)으로 잠근 뒤
플레이 종류 9 · 장면 상태 0x17(수비 인플레이)로 넘어간다 — **"포수 뒤로 빠진 공"(폭투·포일)으로 읽는 것이 가장 맞다(유력)**.
**견제 리드 폭은 원본에 아예 없다(확정)**: 주자는 루 좌표(`0xd78f0`)에 비트까지 정확히 서고, 도루 표시가 켜진 주자만 루를 떠난다.
남은 것은 (a) 0.1% 사건의 *이름*을 못 박을 연출·기록 증거, (b) 플레이 결과 코드 **9** 의 야구적 뜻, (c) 상태 8 의 `야수+0xb4`·`P+0x164` 칸 뜻이다.
앞 노트를 뒤집는 것 7건은 8절에 모았다(그중 P2 의 "35% 넘게 간 주자" 방향 반대, `+0x130` 은 포인터가 아니라 번호, 상태 0xe 는 `state[0x27]` 이 크다).

## 0. 먼저 잡고 가는 전제 — 플레이 객체 칸 이름

| 칸 | 뜻 | 근거 |
|---|---|---|
| `P+0x18` | **야수 9명 포인터 배열** (`[P+0x18][i]`) | 0xb2734 `ldr r3,[r0,#0x18]; r3=[f<<2 + r3]; [r3+0xe0]=1` |
| `P+0x20` | 주자관리(runner manager) 객체 | 0xb4948 `ldr r0,[r1,#0x20]` → 0xa9564/0xa9598 호출 |
| `P+0x24` | 공 객체 | 0xb49fa |
| `P+0x28` | 경기 상태 state(전역 0x1552d0c) | 0xb4358 → `state[0x31+state[0xa]]` |
| `P+0xf0`(4워드) | **루 0~3 을 커버하는 야수 번호** | 0xb3a68 `[P+0xf0+(루%4)*4]` |
| `P+0x130` | **공을 쥔 야수 "번호"(포인터 아님)** | 0xb2734 가 `[P+0x18]` 의 첨자로 쓴다 |

> **정정 1**: P2 1c/2b 의 `+0x130 = f(고른 야수)` 는 *포인터*가 아니라 **야수 번호(0~8)** 다.
> 0xb2726 이 `str r1,[P+0x130]` 한 뒤 바로 0xb2734 에서 `r1<<2 + [P+0x18]` 로 포인터를 얻는다.
> 상태 8·9 분기가 `j(루프 첨자) == [P+0x130]` 을 비교하는 것도 이것으로만 말이 된다.

## 1. AI 상태 8 = **협살(rundown, 런다운)** — **확정**

분기표 `0xd8808`[8] = `0xb48b6`. 상태 8 은 P2 가 추측했던 "+0x1ec 계열"이 맞고, 그 정체는 **협살**이다.

### 1-1. 협살 기록칸 `P+0x1ec` ~ `P+0x1f3` (8바이트) — 확정

`0xb3a04(out, P)` 가 이 8바이트를 만든다 (`0xb3a0e`~`0xb3a1a`: 먼저 8바이트 전부 −1 로 memset, 헬퍼 `0x1400428`).

| 칸 | 뜻 | 만드는 줄 |
|---|---|---|
| `+0x1ec` (=out[0]) | 주자의 **현재 루**를 커버하는 야수 번호 | 0xb3a6c~0xb3a6e |
| `+0x1ed` (=out[1]) | 주자의 **목표 루**를 커버하는 야수 번호 | 같은 루프 i=1 |
| `+0x1ee` (=out[2]) | 주자의 현재 루 = `주자+0x7c` | 0xb3a3c/0xb3a40 |
| `+0x1ef` (=out[3]) | 주자의 목표 루 = `주자+0x8c`; **현재 루와 같으면 +1** | 0xb3a3e~0xb3a4c |
| `+0x1f0` (=out[4]) | **협살 대상 주자 번호** | 0xb3a4e |
| `+0x1f1` (=out[5]) | 0/1 = 두 야수 중 **지금 공을 쥔 쪽**, 없으면 −1 | 0xb3a78~0xb3a7c (`야수번호 == [P+0x130]`) |
| `+0x1f2`,`+0x1f3` | 안 씀(−1 그대로) | |

### 1-2. 협살 대상 주자 고르기 `0xb398c(P)` — **확정** (P2 의 "35%" 수치를 식까지 확인)

```
for i = 주자수(0xa9598(주자관리)) − 1 ... 0:          ; 뒤 주자부터
    R = 0xa9564(주자관리, i)
    if R+0x96(=+0x78+0x1e) != 0: continue             ; 이미 끝난 주자
    if R+0x94(=+0x78+0x1c) != 0: continue
    a = 0xbefec(R)      ; ★ 지금 자리에서 목표 루까지 **남은** 틱 = R.vt0x1c(R+0x2c)
    b = 0xbf01c(R)      ; ★ 출발점(R+0x14)에서 목표 루(R+0x2c)까지 **전체** 틱, 0 이면 건너뜀
    if (100*a)/b > 0x23(=35): return i                 ; ★ 남은 비율 35% 초과
return −1                                              ; 0xb39e4 `movs r0,#1; rsbs r0,r0,#0`
```
→ **"다음 루까지 아직 35% 넘게 남은 주자 중 가장 뒤 주자"**. 35 는 `cmp r0,#0x23` 즉시값(0xb39d8)으로 **박혀 있다**(설정·난이도 아님).

> **정정 3**: P2 "남은 것"·1c 요약의 "**35% 넘게 간** 주자에 협살" 은 방향이 반대다.
> `0xbefec`(0xbefec~0xbf016) 은 `self.vt0x1c(self+0x2c)` 즉 **남은** 틱이고, `0xbf01c` 는 `dist(self+0x14, self+0x2c)/self+0x3c` 즉 **전체** 틱이다.
> 따라서 조건은 `남은/전체 > 35%` — **루에 35% 미만으로 붙은 주자는 협살하지 않는다**. (협살은 "루에서 멀리 떨어진 주자" 에 거는 것이라 의미도 이쪽이 맞다.)

### 1-3. 협살 시작 `0xb3a94(P)` — 확정

1. `0xb3a04` 로 8바이트를 만들어 `P+0x1ec` 에 그대로 복사(0xb3aa8~0xb3ab0).
2. i=0,1 검사: `루 = sb[P+0x1ee+i]` 가 −1 이거나 `[P+0xf0+(루%4)*4]` 가 −1 이면 **중단**(0xb3ab8~0xb3adc).
3. 두 야수에 대해: `야수+0xb4 > 0` 이면 건너뛰고(동작 중), 아니면 `야수.vt0x10()`(0xa124c, 동작 정지) 뒤
   **`0xb8dbc(야수+0x80, 8)` = AI 상태 8 지정**(0xb3b08~0xb3b20).

### 1-4. 언제 시작하나 — 확정

플레이 틱 `0xb401c` 안 0xb433c~0xb4378:
```
if sb[P+0x1f0] == −1:                 ; 협살 진행 중이 아니고
    if !0xb3fa8(P): skip              ; 협살 가능 검사
if state[0x31 + state[0xa]] == 1:     ; ★ 수비 팀이 CPU 일 때만
    0xb3a94(P)                        ; 협살 시작
```
`0xb3fa8(P)` = `0xb398c` 가 −1 이 아니고, `out[5] != −1` 이며 공 쥔 야수가 out[0]/out[1] 중 하나일 것(0xb3fc2~0xb3fe2).
→ **협살은 사람이 수비할 때는 절대 안 일어난다.** (Q1 의 `state[0x31+팀]==0 = 사람` 규약)

### 1-5. 협살 종료 `0xb26b8(P)` — 확정

`memset(P+0x1ec, 0, 8)`(0xb26c8) → `P+0x1f0 = −1`(0xb26d6) → 야수 9명 중 **상태(+0x84)가 8 인 야수는 전부 상태 0 으로**(0xb26da~0xb26f6, `0xb8dbc(f+0x80, 0)`).
부르는 곳: 아웃 판정 0xb3946, 플레이 틱 0xb4336, 그리고 상태 8 자신(0xb4912).

### 1-6. 상태 8 매 틱 처리 `0xb48b6` — 확정 (j = 야수 번호)

```
짝 = (j == sb[P+0x1ec]) ? sb[P+0x1ed] : sb[P+0x1ec]        ; 0xb48b8~0xb48e6
rd = 0xb3a04(지역8바이트, P)                                 ; 매 틱 새로 계산
if 0xb398c(P) == −1 or (rd[0] != j and rd[1] != j):
    0xb26b8(P); 끝                                          ; 0xb4910 — 내가 빠지면 협살 해제
R  = 0xa9564(주자관리, sb[P+0x1f0])                          ; 협살 대상 주자
F2 = [P+0x18][짝]                                            ; 짝 야수

if j == [P+0x130]:                                           ; ── 내가 공을 쥐었다
    내가커버 = (j == [P+0xf0 + (R+0x7c)%4 * 4])              ; 주자 "뒤쪽" 루를 내가 보는가
    안전    = ( R.vt1c(F2.위치) > F2쪽.vt b4(나)+5 )          ; 0xb49b2~0xb49da
    if 야수+0xe0 == 0:                                        ; 아직 포구 전 → 공 쪽으로 이동
        목표 = (P+0x164 == sh[P+0x174]) ? 공+0x2c : 0xa25b0(...)   ; 0xb49e6~0xb4a2e → 0xb4b50
    elif 내가커버 or 안전:  나.vt4c(R)                        ; 0xb4a96 — 주자를 쫓는다(태그)
    elif P+0x12c(공 쥠) != 0:  플레이.vt5c(짝, 0)             ; 0xb4a4a — ★ 짝에게 송구
    else: 아무것도 안 함
else:                                                        ; ── 내가 공이 없다
    t = R.vt1c(내 위치)          ; 주자가 내 자리까지 오는 틱
    u = F2.vt b4(나)             ; 짝이 나한테 던져 공이 오는 틱
    if t >  u+4 : 나.vt4c(R)     ; 0xb4a96 주자를 쫓는다
    elif t > u  : 나.vt0x10()    ; 0xb4aa6 동작 멈추고 대기
    else        : 나.vt48( sb[P+0x1ee + (j==sb[P+0x1ec] ? 0 : 1)] )  ; 0xb4ab0 내 루로 가서 밟기
```
- 야수 vtable = **0xd7934** (vt0x14=0xa14c8 로 역산). 이 절에 쓰인 칸:
  `vt0x10 = 0xa124c`(정지) · `vt0x1c = 0xbf450`(어떤 점까지 걸리는 **틱 수**) · `vt0x48 = 0xa0a18`(루로) ·
  `vt0x4c = 0xa0a5c`(**다른 캐릭터를 쫓아감** — 상대 +0x20 위치를 그대로 `vt0x14` 에 넘김) ·
  `vt0xb4 = 0xa1a60`(**다른 캐릭터 위치까지의 틱 수** — 상대 +0x20 을 `vt0xb8 = 0xa1a98` 에 넘김).
  주자 vtable 0xd771c 의 `vt0x1c` 도 같은 0xbf450(공통 캐릭터 메서드).
- **마법수 두 개**: 공 쥔 쪽은 **+5틱**(0xb49d2 `adds r0,#5`), 공 없는 쪽은 **+4틱**(0xb4a90 `adds r3,#4`) 의 여유를 본다. 서로 다르다 — 원본 그대로.

### 남은 조각 (상태 8)
- `야수+0xb4`(0xb3afa, "동작 중" 으로 보이는 워드)와 `P+0x164` 의 정확한 뜻은 확인 안 함 — **유력**.
- `0xb4b50` 공통 꼬리(좌표로 이동)는 1c 의 `0xa100c` 경로로 보이나 줄까지는 안 읽음 — **유력**.


## 2. AI 상태 9 = **송구 받기(루로 가서 받을 준비) + 송구 실행 게이트** — **확정**

분기표 `0xd8808`[9] = `0xb4838`.

### 2-1. 누가 상태 9 를 세우나 — 확정
송구 함수 `0xb2e38`(= **플레이 vt 0x5c**, 플레이 vtable **0xd8618**) 안 0xb30a2~0xb30d4:
```
F = 받을 야수
if F+0x84 == 9: 아무것도 안 함            ; 0xb30a8 이미 준비 중
P+0x15c = (받을 야수 번호)                 ; 0xb30bc
P+0x158 = sb[P+0x153]  (목표 루 번호)      ; 0xb30c8
0xb8dbc(F+0x80, 9)      ; ★ AI 상태 9      ; 0xb30c6/0xb30cc
F.vt0x48(...)           ; 그 루로 이동      ; 0xb30d0~0xb30d6
```
- 플레이 칸 추가: `P+0x154` = 송구 목표 야수 번호(0xb2e6c), `P+0x134` = 직전 보유 야수(0xb2e74),
  `P+0x158` = 송구 목표 루, `P+0x15c` = 송구 받을 야수 번호.
- `0xb8dbc` 는 함수라기보다 **한 줄 setter** — `str r1,[r0,#4]` + `bx lr`(0xb8dbc). 즉 AI 상태 = `야수+0x84`.

### 2-2. 상태 9 매 틱 처리 `0xb4838` — 확정
```
R  = [P+0x18][ [P+0x15c] ]              ; 송구 받을 야수(= 보통 나 자신)
t1 = R.vt0xc0()                          ; 0xa1c3c = 0xbefec(R) + R+0xcc
                                         ;  = "목표점까지 남은 이동 틱" + R+0xcc(여유)
H  = 0xb0c90(P)                          ; 지금 공을 쥔 야수
b  = [P+0x158] ; 좌표 = 0xd86b0[b]        ; 목표 루
t2 = H.vt0xb8(그 좌표)                    ; 0xa1a98 → vt0xbc = 0xa1adc = ★송구 도착 틱
if t1 > t2: 이번 틱은 아무것도 안 함       ; 0xb488e/0xb4890 — 아직 내가 못 가 있다 → 송구 보류
else:
    if 플레이.vt0x58(b, 0):               ; 0xb4892~0xb48a8 실제 송구
        0xb8dbc(나+0x80, 0)               ; 0xb48ac 내 상태 0 으로
```
→ **상태 9 = "내가 루에 도착하는 시각이 송구 도착 시각보다 늦지 않을 때까지 송구를 미루는 상태"**.
P2 표의 "루 좌표 0xd86b0 으로(+0xac 루 번호, 받기 준비로 보임)" 는 방향은 맞았지만, 이 분기 자체는 **이동을 시키지 않고 송구 타이밍만 잰다**(이동은 상태를 세울 때 `F.vt0x48` 로 한 번 끝났다).

### 2-3. 덤 — 송구 도착 틱의 내야/외야 구분 (**유력**, U-08 과 겹치지 않는 부분만)
`vt0xbc = 0xa1adc`: `[야수+0x88] ≤ 5` 이면 설정 전역 `[0x14000c0]+0x1c`(halfword), 아니면 `+0x1e` 를 곱하고 100 으로 나눈다(0xa1afe~0xa1b16).
→ **내야수와 외야수의 송구 속도 배수가 설정표에서 따로 온다.** (U-07/U-08 은 S7 담당이므로 여기까지만 적는다.)

## 3. AI 상태 0xe = **견제 송구** — **확정**

분기표 `0xd8808`[0xe] = `0xb47da`. 전체가 네 줄이다:
```
000b47da: ldr r1,[sp,#0x28]      ; P
000b47dc: ldr r3,[r1,#0x28]      ; state (전역 0x1552d0c)
000b47e0: adds r3,#0x27
000b47e2: ldr r4,[r2,#0x58]      ; 플레이 vt 0x58 = 0xb2c90
000b47ea: ldrsb r1,[r3]          ; ★ state[0x27]
000b47ec: bl  → 플레이.vt0x58(state[0x27], 0)
```

## 4. 메시지 `0xbc3` 의 처리처 — **확정: 전용 처리기가 없다**

### 4-1. 보내는 곳 (P2 2b 재확인)
플레이 틱 `0xb401c` 안 0xb424a~0xb428e:

### 4-2. 받는 곳 = 경기 장면 vtable 슬롯 12 = **0x509a0** (I-controls 1절)

```
0x509da  cmp 0x586   → bgt 0x50ad2
0x50ad2  cmp 0x6a9   → bgt 0x50b68
```

`0x523aa` 는 `movs r0,#2 ; return` 세 줄짜리 **아무 일도 안 하는 기본 반환**이다(0x523aa~0x523b2).

### 4-3. 그래도 효과가 하나 있다 — 확정

→ **모든 메시지가 CPU 송구 결정을 한 번 돌린다.** 0xbc3 의 유일한 실효는 "송구를 받은 순간 CPU 수비가 다음 송구를 다시 판단한다" 는 것이다.

> **정정 4**: P2 2b 의 "메시지 0xbc3(받음) — 송구 받기 경로" 는 **연출/처리를 부르는 메시지가 아니다.**
> 송구공을 실제로 쥐는 처리는 0xbc3 과 무관하게 `0xb2710`(공 쥐기) 쪽에서만 일어난다.
> 즉 "여기서 쥐기 처리 안 함" 이라는 P2 의 관찰은 맞았고, 그 다음 고리는 **없다**(빠진 분기).


## 5. U-11 — `state[0x19]` 0.1% 사건의 정체 — **동작은 확정 / 이름은 유력**

### 5-1. 굴림 `0x35034(scene)` — 확정 (P2 의 식을 32비트까지 정정)
```

T   = (u16[cfg+0x30] << 16) | u16[cfg+0x2e]           ; ★ 32비트 한 값(정렬 때문에 halfword 둘로 읽는다)

```
`d_level.dat` 실측(`xxd -g2 -e`): 파일 `0x2a` = **10**, `0x2c` = **0** → T = 10.
(칸 대응은 `cfg+N = 파일[N−4]`: 파일 0x14 = 220 = 야수 속도 cfg+0x18, 파일 0x16 = 940 = 송구 속도 cfg+0x1a 로 교차 확인.)

### 5-2. 세우는 곳 `0x3dfac`(상태 0x12 진입 = 공 도착·스윙 판정) — 확정

## 6. U-12 — 견제 순간 주자 리드 폭 — **확정: 그런 값이 없다 (주자는 루 위에 정확히 선다)**

Q1 3b 가 "0x46418 안 2000줄을 다 못 읽어서 못 찾았다" 고 남긴 값이다. 찾았다 — **없다.** 근거 네 가지:

### 6-1. 루 좌표표가 둘인데 내용이 같다 — 확정
| 표 | 쓰는 곳 | 내용 (x, y, z) × 5칸 |
|---|---|---|
| **`0xd78f0`** | `0xa0a18`(vt0x48 루로 이동) · `0xa0ae4`(vt0x58 내가 선 루) · `0xa0b4c` | (20000,0,29445) (25946,0,24175) (20000,0,19170) (14055,0,24175) (20000,0,29445) |
| **`0xd86b0`** | `0xb27ec`·`0xb2c90`·`0xb1900`·`0xb45dc` 등 야수 쪽 | **완전히 같은 15워드** |
주자용·야수용이 따로 있는 게 아니라 **같은 표가 두 벌** 있을 뿐이다. 루에 붙는 오프셋(리드)을 더하는 코드는 어느 쪽에도 없다.

### 6-2. 주자 이동 목표는 루 좌표 "그대로" — 확정

### 6-3. 견제 시작도 주자를 옮기지 않는다 — 확정

### 6-4. 타석 화면에도 리드 연출이 없다 — 확정

### 6-5. 그래서 견제사는 어떻게 나나 — **유력 / 일부 미해결**

| 메시지 0xbc3 | 처리기 없음(기본 반환) + CPU 송구 재판단만 | 해당 없음 |
| `state[0x19]` 0.1% 사건 | 투구마다 0.1%, 무작위 방향 공 + 포수 에러 동작 + 수비 인플레이 | **없음** — 투구 결과가 곧 타석 결과다 |
| `state[0x18]` 스트라이크 존 통과 | `0xcfb7c[난이도]` 상자로 판정 | `pitchTarget.ts` 는 목표점만 만들고 존 상자 판정은 따로 두지 않는다 |
| 도루 | 경기 화면은 Q1 3a 표(0xd047c), 간이 엔진은 E-5 표(0xd9064). 성공/실패는 플레이 종류 5(주자만) | `entities/game/model/steal.ts` — **E-5 표(0xd9064)만** 있고 3루 주자 제외까지 옮겨져 있다. 경기 화면 쪽 표·견제·폭투는 없음 |
| 주자 리드 | **없음(루 좌표에 정확히 선다)** | 없음 — 원본과 같다(우연히 일치) |

### 덤으로 확정한 칸 이름 (앞 노트에 없던 것)
- `P+0xf0`(4워드) = 루별 커버 야수 번호 · `P+0x1ec~0x1f3` = 협살 기록 · `P+0x154` = 송구 목표 야수 · `P+0x158` = 송구 목표 루 · `P+0x15c` = 송구 받을 야수 · `P+0x134` = 직전 보유 야수
- 야수 vtable **0xd7934**, 플레이 vtable **0xd8618**, 경기 로직 vtable **0xd8554**
