## 3. U-58 — 상태 0xc 의 `0xb9` 와 상태 0x18 중계 띠의 `0xc1`·`0x86` — **확정(정정 포함)**

### 3-1. `0xb9` = img_text 프레임 **185 = "스타디움"**
- 그림: 42×10, 흰 글자 (`work/S10/png/U58d.png` 의 185번 줄).
- 쓰는 곳 `0x419b2`: `movs r1,#0xb9` 그대로(자리이동 없음) → 프레임 185.
- **같은 줄에 팀 이름이 먼저 온다**: `0x418c2`~ / `0x4191a`~ 가 `r1 = [팀+0x30](s8) + 0x41` 프레임을 그린다
  (= P6 표의 "프레임 65+팀 = 팀 이름 글씨"). 둘 다 y 는 `0xbaa8c() + 0x2b` 로 같고 x 만 다르다:
  - 팀 이름 → `x0 + 0x19`(+25) (`0x41906`·`0x41956`)
  - 185 "스타디움" → `x0 + 0x64`(+100) (`0x419a6`)
  - `x0 = W/2 − (잰 폭)/2`, 잰 폭은 `0x41830`~`0x4183c` 의 `0xba815(scene+0x1018, 8, 1, →sp+0x34)` 결과
    (`[sp+0x38]` = 폭) = **game_ui 프레임 8 의 폭 171**.
- game_ui **프레임 8** 을 렌더해 보니 **171×25 짙은 남색 둥근 막대**(`work/S10/png/U58f.png`)다.
  W=240 이면 x0 = 35, 팀 이름 60~, "스타디움" 135~177 — 막대(35~206) 안에 딱 들어간다.
- ⇒ 상태 0xc 인트로의 그 줄은 **"〈홈팀이름〉 스타디움"** 한 줄이다. "VS 그림"이 아니다.
  (프레임 **192+구장** = "드래곤즈 스타디움"·"피닉스 스타디움"·"돌핀스 스타디움" 처럼 통글자판도 따로 있는데,
  인트로는 그걸 안 쓰고 팀이름 + "스타디움" 두 조각으로 붙인다.)

### 3-2. `0xc1` 은 프레임 번호가 아니라 **0xc1 << 1 = 386** — img_text 프레임 **386 = "진행속도설정"**
```
00042cc8: c121     movs       r1, #0xc1
00042cd6: 4900     lsls       r1, r1, #1          ; ← 386 (0x182)
00042cd8: 0122     movs       r2, #1              ; 종류 1 = 프레임
00042cdc: bl #0xca9fc                            ; r4 = 0xba759 (그리기)
```
재는 쪽도 같다: `0x42c96`(`movs r2,#0xc1` + `lsls r2,r2,#1`, `r4=0xba815`), `0x42d06` 도 같은 꼴.
- 프레임 386 = **"진행속도설정"** (64×10, 흰 글자 — `work/S10/png/U58c.png`).
  386 자리 이웃: 384 "REVENGE", 385 "공지사항", 387 "대전메뉴".
- 뜻이 정확히 들어맞는다 — 이 띠 바로 옆에 **속도 칸 3개**(R10 7절)가 있다.

### 3-3. `0x86` 은 **그림 번호가 아니다** — 스택 오프셋이다
```
00042ca6: 8620     movs       r0, #0x86
00042cac: 6844     add        r0, sp, r0        ; ← sp+0x86 주소 계산 (잰 결과 읽기)
```
`0x42d70`·`0x42caa` 의 `#0x8a` 도 같은 꼴(`add r6, sp, r6`)이다. 즉 U-58 에 올라 있던 "0x86" 은
**그림 번호로 잘못 읽은 것**이고, 이 띠에서 쓰는 img_text 그림은 386 하나뿐이다.

## 6. U-46 — 작은 지도 주자 점의 game_ui 그림 번호 — **확정: 이미지 21 (13×11 주황 점)**

### 6-1. 구조체 경로를 번호로 풀었다
R15 가 "코드로는 못 읽는다"고 남긴 `[[[scene+0x1018]+8]+8]+0x54` 는 **배열 첨자**다. 같은 함수 안에
번호를 아는 다른 경로가 있어서 대조가 된다:

```
지도 바탕 (0x39632~0x39642)
  00039632: ldr r3, [r6]        ; r6 = scene+0x1018  → PZX 객체
  00039636: ldr r3, [r3, #0xc]  ; +0xc = 프레임 구역
  00039640: ldr r3, [r3, #8]    ; +8  = 배열 머리
  00039642: ldr r0, [r3, #0x24] ; 0x24/4 = 9  → **프레임 9**

주자 점 (0x397ae~0x397b6)
  000397ae: ldr r3, [r6]
  000397b2: ldr r3, [r3, #8]    ; +8  = 이미지 구역
  000397b4: ldr r3, [r3, #8]    ; +8  = 배열 머리
  000397b6: ldr r6, [r3, #0x54] ; 0x54/4 = 21 → **이미지 21**
```
`+0xc` 가 프레임, `+8` 이 이미지라는 짝은 **렌더 결과로 확인**된다:
- game_ui **프레임 9** = 61×59, 원점 (−29,−28), 파트 하나(이미지 20) → **작은 지도 다이아몬드**
  (파란 루 4개를 흰 테두리 선으로 이은 그림, `work/S10/png/U46a.png`). 지도 바탕이 맞다.
- game_ui **이미지 21** = **13×11 주황 점** (`work/S10/png/U46d.png`).
- 반대로 읽으면 말이 안 된다: 이미지 9 는 13×15, 프레임 21 은 92×15(가로 막대)라 지도 바탕도 점도 될 수 없다.
- 이미지 20 이 지도 바탕이고 21 이 바로 그 다음 칸이라는 것도 들어맞는다(같은 묶음에 나란히 있다).

### 6-2. 점의 색 (눈으로 확인)
이미지 21 의 실제 픽셀 색은 네 가지뿐이다:
`#FFD300`(가운데 노랑, 30px) · `#FFA200`(주황, 37px) · `#FF7500`(짙은 주황, 11px) · `#DE3018`(바깥 빨강 테, 25px).

## 7. 글자 그림의 색은 어디서 오나 — img_text.mpl 팔레트 5장 (확정)

`ui/img_text.mpl` 을 풀면 **팔레트가 5장**이다(형식 0x30 = 색 3개짜리 RGB565 묶음 5개):

| 번호 | 0번(투명) | 본체 | 그림자/테 | 눈으로 본 느낌 |
|---|---|---|---|---|
| 0 | `#FF00FF` | `#FFFFFF` | `#EFEFEF` | **흰색** (기본) |
| 1 | `#FF00FF` | `#FFE352` | `#FFB229` | **노랑** |
| 2 | `#FF00FF` | `#F75110` | `#E71818` | **주황–빨강** |
| 3 | `#FF00FF` | `#2949A5` | `#10246B` | **짙은 파랑** |
| 4 | `#FF00FF` | `#7B797B` | `#525152` | **회색**(잠김/비활성) |

`0x913e4/0x913e5(애니객체 [0x1552ae8], n)` 이 이 번호를 고른다(R14 4번 칸과 같은 관용구).
그래서 **그림 자체는 늘 흰 글자 한 장**이고, 화면 색은 그리기 직전 팔레트로 갈아 끼워 만든다.
PNG 로 뽑은 그림이 전부 흰색인 이유가 이것이다.

이번에 확인한 실제 쓰임:
- 교체 화면 제목("투수 교체"/"타자 교체") — `0x38666` `movs r1,#3` → **짙은 파랑**, 그 뒤 `0x386bc` `movs r1,#0` 으로 흰색 복귀.
- 교체 칸 딱지(이름·보직·타율…) — `0x37960` `movs r1,#0` → **흰색**.
- 인트로 "〈팀〉 스타디움", 중계 띠 "진행속도설정" — 둘 다 `movs r1,#0` → **흰색**.
