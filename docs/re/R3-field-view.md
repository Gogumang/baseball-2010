## 요약
**풀린 것(확정)**: ① **필살송구 아웃(기록 36)** 은 0xa810c 한 곳 — 레이저 송구 연출(0x4403c)이 끝나며 +0x1998/+0x1999 를 세우고, 결과 팝업 0x46844 가 결과 코드 0xd(아웃)일 때 state+0x8b=1, 정산 0xa8024 가 아웃 이벤트 ≥1 이면 +1(레이저가 그 아웃을 직접 만들었는지는 안 본다).
② **슬라이딩의 이득**: +0x31c 는 효과음 "한 플레이 한 번" 잠금일 뿐이고, 실제 효과는 0xa96ec → 0xa9690 — **진행률 71~94% 주자 전원이 동작 6(슬라이딩)으로 바뀌고 속도 +40/틱**(0xa0164). 송구가 오는 루로 6틱 안에 닿는 주자는 제어기 vt10 = 0xb030c 가 **매 틱 자동 슬라이딩**(P2 5a 의 미확인 칸).
③ **속도 단위**: 주자 속도 = cfg+0x14(**300**) + ⌊주루×7/100⌋ (+팀 등급, 모드 1·2·8) — 주자 vt64 0xa092c. 야수 220, 둘 다 월드 단위/틱 같은 이동식(0xbf158). 주자는 가장 느려도 야수의 1.36배.
④ **카메라**: this+0x1e8 이 따라가기형(20%/틱, 0xc0690) 또는 데드존형(가장자리 1/8, 즉시 컷) — 전역 [0x14000bc]+0xc 로 고름. 목표 = 대상 − 시야/2 를 [0, 40000−Vw]×[0, 32500−Vh] 로 자름(0xc062c). 대상 = 공 (x, z−높이), 플레이가 끝나고 공이 멈추면 타자주자. 진입 때 즉시 맞춤, 경기 끝 직전엔 투수판 쪽으로 1%/틱.
⑤ **야수 동작 번호 이름** 전부(0 서기 · 1~4 방향 달리기 · 5 송구 · 6 낮은 공 포구 · 7 가슴 포구 · 8~0xb 방향별 몸 날리기 · 0xc 제자리 포구 · 0xd 공 놓침(효과음 53) · 0xe 점프 캐치 · 0xf~0x12 방향별 슬라이딩 캐치), **외야 코드 7 = 1루 쪽(우익 자리), 8 = 3루 쪽(좌익 자리), 9 = 중견**(기록 번호와 7·9 가 뒤바뀜; 코드 1 = 지명타자).
⑥ (추가) **마선수 수비 그림**: 투수 칸은 현재 투수가 마선수면 `ace/defender_{psyker…dragona}`[+0xa&0x1f], 다른 칸은 그 선수가 마선수면 팀의 첫 타자 마선수 번호로 적재한 `ace/defender_{medica…tiger}`. ⑦ (추가) vtable 0xd775c·0xd77c0·0xd7a0c 는 주자(0xd771c)·야수(0xd7934) vtable 의 중간 칸 — 메서드 표를 8장에 정리.
**남은 것**: [0x14000bc]+0xc(카메라 종류)를 쓰는 곳, 작은 지도 점 모양, 야수 동작 0x78(프레임 14)을 거는 곳, 주자 방향 동작 2~5 의 화면 방향 이름, 부착 효과(주자·야수 vt6c~84)가 무슨 그림인지, 기록 36 이 어느 선수·팀 몫인지(0xa77f0 내부). I-controls 정정 1건: 주자 클래스 vtable 은 0xd7afc(공)이 아니라 0xd771c.


## 0. 출발점 (선행 문서에서)
- I-controls 1b: 배율 0xb9474 (this+0x1f0 = 40000×32500→620×500, +0x1f8 → 148×142). 카메라 대상 this+0x1e8(0xc0124 객체), 화면 오프셋 this+0xfec/+0xff0, 움직이면 0x40aec 가 전역 0x1400068 에 (dx,dy).
- I 3b: 슬라이딩 OK → 0x585 → 0x518da → 주자관리+0x31c = 1, 0xa9fd0 이 지움. 읽는 곳 미발견.
- P2 1c: 야수 달리기 +0x3c = cfg+0x18 = 220/틱 (능력치 무관). 940+8g 는 송구 속도. 주자 +0xa4 = 주루×7/100(+팀 등급).
- E 2절: 기록 지급 함수 0xa77f0(ctx, 기록번호). 필살송구 아웃 = 기록 36 (StrGAME[44] = 32+… 기록달성 문구 구간).

## 5. 필살송구 아웃 기록(기록 36 = StrGAME[44]) — **확정**(경로·조건)

기록 번호 36 = 0x24 (StrGAME[44] "필살송구 아웃", 기록 번호 + 8 = 문구 칸, K 노트 G 표 36번 = 필살송구 3G).
0xa77f0(ctx, 번호) 호출지 23곳 중 r1 = 0x24 는 **0xa810c 한 곳**(플레이 정산 0xa8024 안)뿐이다.

흐름 (전부 경기 장면 this 기준):
1. 레이저 실행 0x400bc (I 2d): `+0x1992 = 0, +0x1991 = 1, +0x1990 = 1, +0x1993 = 1`, 플레이 vt64(1).
2. 레이저 연출 0x4403c (매 프레임, `+0x1990` 이 설 때만): 단계 `+0x1992`(s8)
   - 0: `+0x1997 = +0x19ad = +0x19ae = 0`, 단계+1 (0x44110~0x44144)
   - 1: 효과 0xbb39d(100, …), `+0x1993 = 0`, 단계+1
   - 2: 단계+1
   - 3: 단계 = −1, **`+0x1990 = 0`, `+0x1998 = 1`, `+0x1999 = 1`** (0x44166~0x4417e)
3. 결과 팝업 0x46844 (호출 0x46c88 → 0x46de4; 타이머 `+0x108c` > 0 동안):
   ```
   46892: if +0x1997 == 0 && +0x10ac == 0xd :          ; 이번 플레이 결과 코드가 0xd(아웃)
   468d0:    if +0x1998 : 특수 문구 그리기(0xba759, 그림 +0x101c)   ; "필살송구" 표시로 보임
   46922:       if +0x1999 : [0x1552d0c]+0x8b = 1 ; +0x1999 = 0
             else (그 밖): +0x1999 = +0x1998 = 0 ; +0x1997 = 1 ; 보통 결과 그리기 0x393b4
   ```
   `+0x10ac`(결과 코드)·`+0x108c = 10`(표시 타이머)·`+0x1088 = 플레이+0x130(공 가진 야수)` 은 플레이 끝 메시지 처리 0x51408(0x51a56~0x51a80)이 쓴다. 0xd = 아웃 결과(P2 2b: vt90 아웃 → 코드 0xd).
4. 플레이 정산 0xa8024:
   ```
   a8096..a80f6: out = 이벤트(5 삼진 · 0xd 아웃) 개수        ; sp+0x30
   a80f8: if out > 0 && state[0x8b] != 0 :
   a810a:     0xa77f0(ctx, 0x24)        ; 기록 36 필살송구 아웃
   a8116:     state[0x8b] = 0
   ```
   state+0x8b 는 플레이 초기화 0xb67d0(0xb680c) 에서도 0 이 된다. +0x8b 를 쓰는 곳은 0x46932(=1)·0xa8116·0xb680e(=0) 셋, 읽는 곳은 0xa8102 하나 (전체 디스어셈에서 `#0x8b` 전수 검색).

→ **규칙: 레이저(필살) 송구가 나온 플레이가 "아웃" 결과(코드 0xd)로 끝나면, 그 정산에서 아웃 이벤트가 1개 이상일 때 필살송구 아웃 +1 (한 플레이 한 번).**
   레이저 송구 자체가 그 아웃을 만들었는지는 따지지 않는다(같은 플레이 안의 아무 아웃이나). 레이저 발동은 사람 수비가 반짝임 창에서 키를 눌러야 하고 CPU 수비면 자동(I 2d). 기록이 어느 쪽 팀·선수 몫으로 적히는지는 0xa77f0 내부라 이번에 안 봤다.
- 남은 고리(유력): `[0x1552d0c]` 가 0xa8024 의 `ctx+8`(state) 와 같은 객체라는 점 — +0x8b 의 유일한 쓰기·읽기 짝이라 사실상 확정.
- 웹판: `gameRecords.ts` 에 기록 36 판정 없음 (수비 화면·레이저 송구 자체가 없다).


## 3. 슬라이딩의 실제 이득 — **확정**: 진행률 71~94% 주자에 **틱당 +40 속도**(슬라이딩 동작 6). +0x31c 는 효과음 "한 플레이 한 번" 잠금일 뿐

### 3-1. 주자관리 구조와 +0x31c
- 주자관리(경기 장면 +0x20c) 생성자 0xa9260/0xa9294: vtable 0xd8308, **주자 4명을 +0x18 부터 0xc0 바이트씩 안에 품는다**(주자 생성자 0x9fe10, **주자 vtable 0xd771c**). +0x18+4×0xc0 = +0x318 에서 주자 칸이 끝나고 +0x31c 가 그 뒤 바이트.
  (I-controls 3b 의 "주자 클래스 vtable 0xd7afc" 는 **공** 클래스다 — 0xd7afc 슬롯 0x24 = 0xa28c0 공 물리. 주자 클래스는 0xd771c, 틱 vt0c = 0xa01cc.)
- +0x31c 를 만드는 `movs rX,#0xc7 ; lsls rX,rX,#2` 를 **원시 바이트 전수 검색**(짝수 정렬 전부) + 리터럴 0x31c(0곳)로 찾으면 주자관리 쪽은 셋뿐: 0xa9250(생성·초기화 =0), 0xa9fd0(상태 0x17 진입 0x46418 이 부름: =0, 모든 주자 +0xb8=+0x98=0), 0x51980(슬라이딩 처리: 읽고 1 로 씀). → +0x31c 는 **슬라이딩 효과음을 한 플레이에 한 번만 내게 하는 잠금**이다(슬라이딩 자체는 아래 3-2 처럼 잠금 검사 전에 걸린다).

### 3-2. 실제 효과는 "달리는 주자 수" 로 보였던 0xa96ec 안에 있다
- 슬라이딩 처리 0x518da (메시지 0x585):
  ```
  플레이 종류 2·3 → 끝 ; 0xb68dc(경기 끝남) → 끝
  아웃돼 퇴장 중인 주자(+0xba && !+0xbb) 가 있으면 → 끝
  n = 0xa96ec(주자관리) ; n ≤ 0 → 끝                  ; ← 여기서 슬라이딩이 실제로 걸린다
  소리 재생 중(0x6e575) → 끝 ; +0x31c != 0 → 끝
  +0x31c = 1 ; 효과음 10
  ```
  (주의: 소리·잠금 검사가 0xa96ec 호출 **뒤**라, 이미 +0x31c 가 서 있어도 두 번째 누름에서 슬라이딩 자체는 또 걸린다 — 효과음·잠금만 한 번. 원본 그대로.)
- 0xa96ec(관리): 주자 i 마다 0xa96d0 → **0xa9690(관리, 주자)** 를 불러 참인 수를 센다.
  ```
  a9690: 주자 없음 또는 주자+0x96(아웃) → 0
         p = 주자.vt90()            ; 0xa04e8 = 진행률 %
         p − 71 ≤ 23 (71 ≤ p ≤ 94) → 주자.vt60() ; return 1
  ```
- 주자 vt90 = **0xa04e8 = 진행률(%)** = 거리(출발 루 → 현재 위치) × 100 ÷ 거리(출발 루 → 목표 루) (루 좌표 표 0xd77d8, 거리 0xbfa2c; 0xa05f4~0xa0608 `×0x64` 후 나눗셈). 목표 = 출발 루면 따로 처리.
- 주자 vt60 = **0xa04d0**: `주자+0xb8 = 1`(슬라이딩 중), vt44(6).
- 주자 vt44 = **0xa0164 (동작 바꾸기)**: 새 동작이 지금과 다르면 `속도 = vt64()` 인데 **동작 6 이면 vt64() + 40**(0xa017a~0xa0186 `adds r1,#0x28`), 0xbec7c 로 +0x3c 에 넣는다.
- 슬라이딩 유지·해제: 방향 동작 고르기 0x9ffcc 가 `+0xb8` 이면 늘 동작 6 을 고른다(0xa000e~0xa0016). 새 목표를 받을 때(vt48 = 0xa07b0 → 0x9ff38) `+0xb8` 이면 `+0xb8 = 0`, vt44(0)(보통 속도로). 도착(+0x3b) 때 0xaa008 이 `+0xb8 = 0`. 상태 0x17 진입 때 0xa9fd0 이 전부 지운다.
- 그리기 0x43a0c 도 0x9ff38(슬라이딩 중?) 로 그림을 가른다(동작 6 프레임).
→ **이득 = 다음 루까지 71~94% 온 주자가 남은 거리를 틱당 +40 빨리 달린다**(보통 300+주루×7/100 → +40, 4장 참고). 1루 가는 길(≈7945) 기준 71% 지점에서 남은 ≈2300 을 335/틱 대신 375/틱 → 약 0.7틱 이득. 태그·포스 판정(0xb36d0)에 +0xb8 를 보는 곳은 없다 — 오직 도착 틱이 당겨지는 효과.

### 3-3. 자동 슬라이딩 — 제어기 vt 0x10 = 0xb030c (P2 5a 의 "(미확인)" 칸)
- 경기 장면 틱 0x524c0 안 0x52670: **매 틱** `n = 0xaf8fc(제어기)` (= 제어기.vt10(설정+3 바이트, 안 씀)), n > 0 이면 효과음 10. 사람/CPU 구분 없이 돈다(제어기 = 경기 장면 +0x210, 0x3ea80 에서 확인).
- 0xb030c:
  ```
  공(제어기+0x14).vt18() 참 → 0                       ; 공이 날아가는 중일 때만
  계획 = 플레이(제어기+0xc)+0x14c 의 8바이트 ; T = 계획[+0xd](s8) − 공+0x68(현재 틱) ; b = 계획[+0xf](s8, 송구 목표 루)
  주자마다: b ≠ −1 && 주자+0x7c(목표 루) == b 이고
            t = 0xbefec(주자)(도착까지 틱) ; |t − T| ≤ 9 && t ≤ 6 && !슬라이딩 중(0x9ff38)
            → 0xa9690(관리, 주자)  (진행률 71~94% 면 슬라이딩)
  return 슬라이딩 시킨 수
  ```
  → **송구가 향하는 루로 6틱 안에 닿는 주자는 키 없이도 자동으로 슬라이딩한다**(송구 도착 예정과 ±9틱). 사람 키 슬라이딩은 그 밖의 상황(송구가 안 오는 루, 7틱 이상 남음)에서 미리 당기는 용도다.
- 웹판: 없음. 옮긴다면 사람 키(OK) = 0xa96ec, 자동 = 0xb030c 를 매 틱.

### 3-4. 덤 — 주자 +0xba/+0xbb/+0xbc = 아웃 주자 퇴장 연출 (확정)
0xaa008(주자관리, 매 틱)이 아웃(+0x96)이고 +0xba·+0xbb 가 0 인 주자에 0xa03ac: `+0xba = 1, +0xbb = 0`, x > 20000 이면 `+0xbc = 1`·동작 5, 아니면 동작 4, `+0xb4 = 0`.
주자 틱 0xa01cc 는 그동안 x 를 **틱당 ±150** 옮기고(1루 쪽 +, 3루 쪽 −) `+0xb4` > 10 이면 `+0xbb = 1`. 슬라이딩 처리의 "+0xba && !+0xbb 면 무시" = 아웃 주자가 걸어 나가는 동안은 못 누름.

## 4. 주자·야수 속도 단위 — **확정: 둘 다 "월드 단위/틱", 같은 이동식**

- 이동식은 둘 다 기반 캐릭터 vt 0x24 = **0xbf158**(주자 vtable 0xd771c 슬롯 0x24 = 0xbf159, 야수도 같음): 목표점으로 직선, 틱마다 `+0x3c` 만큼. 도착 틱 0xbf01c = 거리 ÷ `+0x3c`.
- **주자 속도가 +0x3c 로 들어가는 길**: 주자 vt64 = **0xa092c** = `cfg[+0x14](s16) + 주자[+0xa4]`.
  ```
  a092c: ldr r3,=0x14000c0 ; adds r0,#0x78 ; ldr r0,[r0,#0x2c]   ; 주자+0xa4
         movs r2,#0x14 ; ldrsh r3,[cfg,r2] ; adds r0,r3,r0        ; + cfg+0x14
  ```

```
obj = this+0x177c (없으면 new) ; 0x76a08(obj) ; 0x7998c(obj)               ; 이전 투수 마선수 그림 풀기
0x79a54(obj, x, defender, defender.mpl)
p = 0xae83c(팀)                          ; 그 팀 현재 투수
p 가 마선수 → 0x79ab0(obj, p 의 번호)     ; 투수 마선수 그림
q = 0xb8a50(팀, 0x40)                    ; 팀 선수 목록에서 +0xa & 0x40 인 첫 선수
q 있음 → 0x79a5c(obj, q 의 번호)          ; 타자 마선수 그림 — 팀당 하나만 적재
```
같은 적재가 0x3fe68(두 객체씩, 0x3ff3a~0x3ffdc — 두 팀), 0x47cc8(경기 장면 적재 0x4834e·0x48378), 0x48480(0x485ca, 투수만)에도 있다.

### 7-3. 그리기 (0x43278 야수 9명 루프 → 0x79b48(obj, a, b, 플래그, …))
```
a (0x43336~0x43354) = 칸 0(투수) 이고 0xae83c(this+0x224 팀) 가 마선수   → +0x28 그림(투수 마선수)
b (0x4335c~0x43378) = 칸 ≠ 0 이고 야수+0xec(선수) 가 마선수               → +0x1c 그림(타자 마선수)
그 밖                                                                       → +0xc 보통 그림 + +0x10 팔레트
c (0x4337a~0x4339c) = 칸 ≠ 0 이고 선수 +0xb 상위 니블 ∈ {2,3}(비트 0x20 = 좌타/좌투로 보임 — 유력) → 0x79b48 인자 (반전 쪽으로 보임)
0x79b48: a 면 +0x28, 아니고 b 면 +0x1c, 아니면 +0xc/+0x10 ; a 가 아니면 그리기 플래그에 +0x11(좌우 반전 비트) 가 더해진다
```
- 프레임 번호(동작 → 프레임, 2-1 표)는 세 그림 모두 같은 식을 쓴다 — 마선수 그림도 000~124 칸 배치가 같다고 봐야 한다(그림 파일로 확인 안 함).
- 주의(원본 그대로): 타자 마선수 그림은 팀당 **첫 번째 마선수 하나**만 적재되므로, 한 팀에 타자 마선수가 둘 이상이면 둘째부터도 첫째의 그림으로 그려진다(b 는 "마선수인가" 만 본다).
- 웹판: `ace/defender_*` 를 전혀 참조하지 않는다(Q0). 수비 화면이 없으니 붙일 곳도 아직 없다.

## 8. vtable 0xd775c · 0xd77c0 · 0xd7a0c — **정체: 독립 vtable 이 아니라 주자·야수 vtable 의 중간 칸**

- **0xd775c = 주자 vtable 0xd771c + 0x40**(vt40), **0xd77c0 = 0xd771c + 0xa4**(vta4), **0xd7a0c = 야수 vtable 0xd7934 + 0xd8**(vtd8). Q0 가 함수 포인터로만 잡은 0xa0070~0xa0780·0xa0940~0xa0e08·0xa2178 은 이 두 클래스의 메서드다(궤적 계산 아님).
- 주자 vtable 0xd771c 는 0x00~0xa8 (43칸), 이어서 0xd77c8 에 +0x78 부분객체용 보조 vtable(오프셋 −0x78, 0xa0960·0xa0970). 야수 vtable 0xd7934 는 0x00~0xe4, 이어서 0xd7a1c(−0x78)·0xd7a30(−0x80)·0xd7a40(−0x9c) 보조 vtable.
- 두 클래스가 같은 기반(0x9fxxx~0xa0cxx)을 나눠 쓴다: 슬롯 0x08·0x18~0x3c(0xbfxxx 캐릭터 기반), 0x48~0x58, 0x68~0x84 가 같은 함수.
