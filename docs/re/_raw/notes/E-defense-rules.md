# E. 수비 판정·경기 규칙 잔여 (binary.mod 역분석)

## 요약

**풀림(확정)**: 미션 시작 볼카운트 순서(웹 생성기와 같음) · 미션 조건코드 1~3 = 투수 미션 조준점 흔들림 세기(0x39c5c) · 간이 엔진 부호 난수 rand(0,2)(웹과 같음) ·
상대 타순은 이닝을 넘어 이어짐(웹과 같음) · 뜬공/직선타 구분 없음(단, 원본 간이 엔진엔 **희생플라이도 없음** — 웹은 넣었다) ·
땅볼 진루타 주자 순서(웹 "3루 비었으면" 과 같음, 난수 뽑는 조건만 다름) · **연장 상한 없음·무승부 불가**(웹 14회 상한과 "동점→홈 승" 은 원본에 없음) ·
**웹 연장 보정·14회 강제 스윙이 한 이닝 빠름**(원본 이닝은 0부터: 11회부터 보정, 15회 강제 스윙) · 순위 마지막 기준(위치 기준 선택 정렬 + 상대전적 색인 버그) ·
병살·삼중살 식(한 정산의 아웃 이벤트 2/3개) · **그라운드 홈런은 존재하고 홈런으로 센다**(웹은 3루타).
**유력**: CPU 투수 교체 AI(0xc1ba4·0xac428, 웹에 없음) · 도루 저지 판정 식 · CPU 경기 도루(성공만, 실패 없음 — 웹 간이 엔진엔 도루 자체가 없음) ·
하루치 경기 0xc2a48 승패 비교가 읽은 그대로는 뒤집혀 보임(재확인 필요).
**미해결**: 수비 시뮬레이션의 수비수 이동·포구·주루 판단 식(물리·송구·악송구·플레이 끝 분류·수비수 능력 공식까지는 확인, 1절).

도구 메모: 함수 호출은 대부분 `ldr rN,=함수|1` + `bl 0xca9f4/0xca9f8/0xca9fc/0xcaa00/0xcaa04`
(각각 bx r2/r3/r4/r5/r6 베니어) 라 `re xref` 는 리터럴 풀 쪽으로 잡힌다.
난수 0xbfa54 = rand(a,b): 시드 LCG `s = (s*0x343fd + 0x269ec3) >> 1`, a + s mod (b−a) → [a, b).

## 4b. 미션 시작 상황 — 볼·스트라이크 순서 — **확정**

- 0xaae7c (미션 시작 상황 적용), r6 = 미션 레코드, [ctx+0x10] = 경기 상태(state):
  ```
  aaf70: ldrb r3,[r6,#4]; ands r3,#3        ; 비트0-1 → strb [state,#6]
  aaf78: ldrb r3,[r6,#4]; lsls #28; lsrs #30 ; 비트2-3 → strb [state,#5]
  aaf82: ldrb r3,[r6,#4]; lsls #26; lsrs #30 ; 비트4-5 → strb [state,#4]
  ```
- state 칸 뜻은 투구 판정 0x9d57c 로 확정:
  ```
  9d598: ldrsb r3,[state,#4]; cmp r3,#1; ble → 1(스트라이크) 아니면 5(삼진)
  9d5a8: ldrsb r3,[state,#5]; cmp r3,#2; ble → 2(볼)     아니면 3(포볼)
  ```
  → state+4 = 스트라이크, state+5 = 볼, state+6 = 아웃.
- 결론: 레코드 바이트 4 = `아웃(비트0-1) | 볼(비트2-3) | 스트라이크(비트4-5)`.
- 웹판: `tools/generate_game_data.py:450-451` (`balls: (count >> 2) & 3, strikes: (count >> 4) & 3`) — **원본과 같다.** "볼·스트라이크 순서 추정" 표기는 떼도 된다.
- 덤: 바이트 5 주자는 같은 함수에서 비트2 / 비트1 / 비트0 을 따로 떼어 0xa9a9c(주자 배치)에 넘긴다(aafa2~aafba). 생성기의 4=1루·2=2루·1=3루 와 순서 일치(인자 순서로 본 판단, 0xa9a9c 내부는 안 읽음 — 유력).
- 바이트 3 하위 4비트 = 시작 이닝(−1), 상위 4비트 = 팀 선택(0xaa5e8 `lsrs #4` → 0xb6c19 인자).
- 바이트 7 = 두 팀 시작 타순 (상위 4비트·하위 4비트 → 각 팀 +0x32, 0xaa87c~0xaa89e).

## 4a. 미션 조건코드(레코드 바이트 13) — **확정: 투수 미션의 조준점 흔들림 세기**

- 읽어 두는 곳: 0xaa57c `aa6c2: ldrb r3,[rec,#0xd]; str r3,[ctx,#0x20]`. 미션 컨텍스트 ctx 는 화면객체 **[+0x1788]** 이 가리키는 객체다
  (0x3f892~0x3f8c4 가 `this=[화면+0x1788]` 로 0xaa57c 를 부른다 — 앞서 "화면+0x70" 이라 적은 것은 두 번째 인자였다).
- 쓰는 곳: **0x39c5c** = 투수 조준 상태의 틱 갱신 (화면 상태 분기 0x52c50 → `0x52e54: bl 0x39c5c`, 조준하는 동안 매 틱).
  ```
  조준 x(+0x10b8) += 입력dx×20, y(+0x10bc) += 입력dy×20
  존 중심 표 0xcfbcc[구질/좌우 +0x17e1]×12 (예: (19415,1202)·(20585,1202)) 기준 x ±600, y ±400 으로 자름
  if [화면+0x1788] != 0 && [화면+0x1104] == 5 (투수 미션):
     switch ctx+0x20:
       1: if rand(0,100) <= 50: x += rand(-40,40)
       2: if rand(0,100) <= 50: x += rand(-80,80); y += rand(-80,80)
       3: if rand(0,100) <= 50: x = rand(중심x-600, 중심x+600); y = rand(중심y-400, 중심y+400)
  ```
  (0x39d24~0x39dde. rand(a,b) 는 [a,b).) 즉 **1 = 가로로 약하게 흔들림, 2 = 가로·세로로 크게 흔들림, 3 = 틱마다 51% 로 조준점이 존 안 아무 데로 튐.**
- 붙은 미션: 투수 4 로제(6구 삼진)=1 · 투수 5 "흔들리지 않는 마음"(무실점 3아웃)=1 · 투수 8 크라이져(5구 삼진)=2 · 투수 12 킹타이거(4구 삼진)=2 · 투수 10 "난공불락의 철벽마무리"(무안타 3아웃)=3. 타자편은 모두 0(효과 없음).
- 웹판: `missions.ts` 의 `conditionCode` 는 읽기만 하고 쓰지 않는다 (generate_game_data.py:392-394 주석 "뜻은 미해독"). 투수편 조준 입력에 위 흔들림을 넣어야 한다.

## 3a. 간이 엔진 부호 난수 — **확정**

- 0xc11f0: `c144c: ldr r3,=0xbfaa1; bl bx_r3` → r0≠0 이면 spreadX 그대로, 0 이면 부호 뒤집기(c1458~c1462). Y 도 같은 방식(c1464~c1478).
- 0xbfaa0 은 인자가 없는 함수다: `movs r0,#0; movs r1,#2; bl 0xbfa54` = **rand(0,2)**. 디컴파일에서 "인자 유실"로 보인 건 이 함수가 원래 인자를 안 받기 때문.
- 웹판 `quickAtBat.ts:146-148` (`randomIntegerBelow(random,0,2) === 0` 이면 부호 반전, X 먼저 Y 나중) — **원본과 같다.** "(추정)" 주석은 떼도 된다.

## 3b. 상대 타순 — 이닝마다 1번부터인가 — **확정: 아니다, 이어진다**

- 팀 객체(0x29c 바이트, 0xc2798 `movs r0,#0xa7; lsls #2`): +0 = 현재 투수 슬롯, +0xe..+0x16 = 타순표, **+0x32 = 현재 타순(0~8)**.
  현재 타자 = 0xae89c: `ldrb r3,[team,#0x32]; ldrb r1,[team+r3,#0xe]; → 0xb8a35(team,r1)`.
- 타석이 끝나면 0xaf020(team, flag): `[+0x291]=1; [+0x293] = ([+0x32]+1) mod 9` (0xca911 = mod) — 0xc11f0·0xc15a4·0xc1818 이 부른다.
  다음 타석 시작 때 0xaebe4 가 대기값을 확정한다 (0xc262c 첫머리 `0xaebe5(team74,0)`·`(team78,0)`).
- +0x32 에 쓰는 곳은 전 바이너리에서 넷뿐: 0xb7c42(팀 초기화 0), 0x3a55a(사용자 경기 시작), 0xaa888/0xaa89e(미션 시작), 그리고 0xaebe4 확정. **이닝 전환에서 0 으로 되돌리는 코드는 없다.**
- 웹판 `simulateHalfInning.ts:26,102` 가 `nextBattingOrderIndex` 를 돌려주고 `leagueDay.ts:57-66` 이 다음 이닝에 넘긴다 — **원본과 같은 방향.** 남은 추정 목록에서 뺄 수 있다. 확정 지점: 0xaebe4 `aedee: strb r2,[team+0x32]` (r2 = [team+0x293], 대기값이 8 이하일 때. 9 이상이면 대타 교체 경로 aecac~aedec).

## 3c. 투수 교체 — **유력: 원본은 CPU 가 투수를 바꾼다 (웹판 "선발 고정" 은 원본과 다름)**

- 간이 타석 루프 0xc262c 는 타석마다 먼저 0xc1ba4 를 부른다 (`c2662: bl 0xc1ba4`). 그 안에서 수비 팀 투수 교체를 판정한다.
- 교체 실행 = 0xaf09c(team, 벤치번호, 즉시) : `[team+0x290]=1; [team+0x292]=벤치번호+1` → 다음 확정 0xaebe4 가
  `team[0]`(현재 투수 슬롯) 과 `team[team[0x292]]` 를 맞바꾼다 (aebfe~aec0e), 벤치 수 `team+0x33` 을 1 줄인다 (aec22~aec32).
  0xaf09c 를 부르는 곳: 0xc1c3c(간이 경기 0xc1ba4), 0xac644(CPU 투수 교체 AI 0xac428), 0x495e0(사람 경기 화면).
- 0xc1ba4 의 두 길:
  1. `state[1]==3` 이고 0xb6ded(state)==2 이고 수비 팀이 CPU 이고 현재 투수가 마선수가 아닐 때:
     벤치(`team+0x33` 명)에서 마선수(0xb6388 = 선수 레코드 +0xa 부호비트)를 찾아 **7회**면 그 투수로 바꾼다 (c1c2e `cmp r3,#7`).
  2. 그 밖: 0x66864() 가 참이면(미션 5·6 의 일부 미션만 거짓) 0xac428(CPU 수비 AI) 를 부른다.
- 0xac428 교체 조건 (r5 = 수비팀 점수 − 공격팀 점수, r6 = 이닝, s = 체력% = `team 투수 +0x2c ÷ 100` (0xaebb0),
  역할 = 투수 레코드 +0xb 하위 2비트 (0xb6704), A = 0xa61b8(ctx,0,수비측) = team+0x284, B = 0xa61b8(ctx,1,수비측) = team+0x280, team+0x27c = 이번 투수 투구 수(0xa5e5e 에서 투구마다 +1)):
  - 벤치 수 ≤ 인자(최소 벤치)면 안 바꾼다. `state[0xd]` 가 서 있으면 안 바꾼다(교체 뒤 1, 투구마다 0 으로 되돌림 0xa5e72).
  - 특수 투수(0xb633c 참): A>2 또는 B>3 또는 s≤39 면 교체.
  - 역할 0·1: A>2 또는 s≤19 면 교체. 아니면 이닝 ≤3: B>4 면 교체 / 4회: B>4 이고 s≤49 면 교체 / 6회: B>2 이고 s≤29 면 교체 /
    5·7회 이상: A>1 이면 교체. 8회 이상은 여기에 더해 `0 < 리드 ≤ 5` 이면 (리드 ≤3 또는 리드 ≤ 주자수+2 일 때) "마무리 상황" 표시 후 교체.
  - 역할 2: A≠0 이고 리드 ≤ −2 면 교체.
  - 새 투수: 마무리 상황이면 0xac360 검사 뒤 벤치 마지막(=벤치 수−1), 아니면 0xabfcc(이닝·상황으로 고름). 마선수 제외 옵션이면 마선수를 건너뛴다.
  - A·B 가 정확히 무엇(피안타/실점/볼넷)인지는 증가시키는 코드를 못 찾아 **미확인**. 0xabfcc·0xac360 내부도 안 읽음.
- 웹판: `leagueDay.ts:49-50` 은 `startingPitcherOf` 로 선발만 쓰고, `simulateHalfInning` 은 투수를 고정해 받는다. 체력(`+0x2c`) 소모도 없다(quickAtBat 의 stamina 는 고정값).
  원본은 투구마다 +0x28(투구 수) 증가, 체력% 로 교체 → **다름**. 이식하려면 0xabfcc·A/B 뜻을 먼저 풀어야 한다.

## 3d. 이닝 번호·연장 상한·동점 — **확정(상한 없음) / 웹판 한 칸 어긋남 발견**

- **경기 상태의 이닝(state+0x6b)은 0부터 센다.** 근거 셋:
  - 0xb6814 가 마지막 이닝 칸 state+0x69 에 **8** 을 넣는다 (`movs r3,#8; strb [r0+0x69]`) = 9회.
  - 미션 레코드 바이트3 하위 4비트를 그대로 +0x6b 에 넣는다 (0xaa688~0xaa69a). 투수 13 "5이닝 노히트노런" = 4 → 5회~9회 5이닝, 투수 14 "6이닝 퍼펙트" = 3 → 4회~9회 6이닝 로 맞는다.
  - 콜드게임 `cmp r3,#5; ble` (0xb694c) = "이닝 > 5" = 7회부터 — 기존 노트 "7회 이후 10점 차" 와 맞는다.
- 경기 끝 판정 0xb68fc (r1 = state+0x7e 원정 점수, r4 = state+0x7f 홈 점수, state[9]=1 이 말 공격):
  ```
  이닝 >= state[0x69](=8, 9회) 일 때만:
    말(state[9]==1): 아웃>2 → 점수가 다르면 끝 / 아웃<=2 → 홈이 앞서면 끝(끝내기)
    초(state[9]==0): 아웃>2 → 홈이 앞서면 끝
  (그리고 콜드게임: 이닝>5 에서 10점 차)
  ```
  **동점이면 절대 끝나지 않는다. 연장 상한 코드는 없다.** 이닝 증가 0xb6b6c 는 `아웃>2 && 말` 이면 +1 할 뿐 막는 값이 없고,
  점수판 0xb6988 은 `이닝 mod 9` 로 칸을 돌려 쓴다(무한 연장 대비). 경기 루프 0xc2760·0xc2a48 도 `while (0xc2198(sim,1))` 뿐이다.
  - 12회·14회 어느 쪽도 원본 상한이 아니다. 대신 간이 엔진이 경기를 끝내게 민다:
    - 0xc13e0: `이닝 > 9`(0부터 → **11회부터**) 이고 세기 > 50 이면 세기 += (이닝−9)×5, 코스 오차 ×3 ÷ trunc(세기/20).
    - 0xc26e0: `이닝 == 0xe`(0부터 → **15회**, 딱 그 이닝만) 이면 투구 판정 경로 없이 스윙 강제.
- **웹판 차이 (한 칸 어긋남)**:
  - `quickAtBat.ts:81` 은 inning 을 1부터로 받는데 `EXTRA_INNING_FROM = 9`(balance.json:187) 와 `FORCED_SWING_INNING = 14`(quickAtBat.ts:41) 를 원본 0-기준 값 그대로 쓴다.
    → 웹은 **10회부터** 보정(+5), **14회**에 스윙 강제. 원본은 11회부터 +5, 15회에 스윙 강제. 1-기준이면 `from=10`, `forced=15` 여야 한다
    (또는 엔진에 inning−1 을 넘겨야 한다). 호출부: `simulateHalfInning.ts:72`, `leagueDay.ts:57,64` (inning 1..).
  - `leagueDay.ts:16` `MAXIMUM_INNINGS = 14` 는 원본에 없는 상한. 상한이 있어서 동점이 생기고, 그래서 `leagueDay.ts:87-89` 에 "동점이면 홈 승" 규칙이 필요해졌다.
    원본대로면 상한 없이 점수가 갈릴 때까지 돈다(무한 루프 안전망이 필요하면 원본에 없는 것으로 표기).
- 동점 처리 (원본 코드상의 모양, 실제로는 동점이 나지 않음): 하루치 경기 0xc2a48 은
  ```
  c2b8a: score(side(B)) → [sim+0x30+k]   ; B = 0xb7845(league,팀)==0 쪽 목록(+0x1c)
  c2b96: score(side(A)) → [sim+0x44+k]   ; A = 0xb7845==1 쪽 목록(+8)
  c2ba6: cmp scoreB, scoreA ; ble c2bba
  c2baa: 0xb76dd(league, A)  ; 승  → 0xb77e1(league, B) ; 패
  c2bba: 0xb76dd(league, B)  ; 승  → 0xb77e1(league, A) ; 패
  ```
  **읽은 그대로면 "B 점수 > A 점수 일 때 A 에 승" 으로 뒤집혀 있다.** 0xb76dd 가 승(승수 +0 칸 +1, 연승 +0xa, 최다 연승 +0x14, 연패 +0x28=0, 상대전적 +0x44)인 것은 0xb77a0~ 로 확인했고,
  포스트시즌 한 경기 0xc2760 (c28e2~c2916) 은 `score(X) > score(Y)` 면 X 승으로 **정상**이다. 0xc2a48 쪽만 반대로 보인다 — 원본 버그일 수 있으나
  score 칸(state+0x7e+slot)과 side(0xb7844) 의 대응을 한 번 더 확인해야 한다 (**유력-낮음**, 재확인 권장).
  동점(도달 불가)일 때는 B(side 0) 가 승이 된다. 웹판의 "동점 → 홈 승" 과 대응시키려면 side 0/1 이 원정/홈 중 어느 쪽인지(0xb7844) 를 더 봐야 한다.

## 3e. 순위 동률 마지막 기준 — **확정 (원본은 위치 기준 선택 정렬, 상대전적 비교에 색인 버그)**

- 0xb802c → 0xb79d8(league, 순서배열). 순서배열 초기값은 표 0xd8a25 = `[0,1,2,...,9]`.
- 0xb79d8: 승 사본(league+0, 10바이트)·패 사본(league+0x1e) 을 스택에 복사해 **선택 정렬**한다.
  ```
  for i in 0..8: best=i
    for j in i+1..9:
      if 승[best] < 승[j]            → best=j
      elif 승 같고 패[best] > 패[j]   → best=j
      elif 패도 같고 h2h[j][best] > h2h[best][j] → best=j     ; h2h = league+0x44+10*행+열
    swap(승[i],승[best]); swap(패[i],패[best]); swap(순서[i],순서[best])
  ```
- **마지막 기준**: 상대전적까지 같으면 best 를 바꾸지 않는다 → 현재 배열 위치가 앞선 팀. 초기값이 팀 번호 순이라 대체로 팀 번호 순이지만,
  앞 단계의 swap 으로 뒤 칸 순서가 섞여 있으므로 엄밀히 "팀 번호 순" 은 아니다 (예: 0번이 i=0 에서 5번 자리로 밀려나면 이후 동률에서 5번 자리 기준).
- **원본 버그**: 상대전적 비교의 j·best 는 정렬 중인 **배열 위치**인데 h2h 표는 **팀 번호**로 되어 있고 함께 섞지 않는다. 한 번이라도 swap 이 일어난 뒤에는 엉뚱한 팀끼리의 전적을 비교한다.
- 웹판 `league.ts:66-73` 은 `Array.sort` 로 승·패·상대전적(팀 번호로 바르게) → 팀 번호. 원본 재현을 원하면 위 선택 정렬(위치 색인 h2h 포함)을 그대로 옮겨야 한다.

## 2. 도루 저지(24)·더블플레이(26)·트리플플레이(27) 판정

기록 지급 함수는 0xa77f0(ctx, 기록번호). 세 기록 모두 **플레이 정산 0xa8024** 안에서 준다. 0xa8024 는 ctx 의
**플레이 이벤트 목록**(ctx+0x30.., 개수 ctx+0x2c)을 훑는다. 이벤트 번호: 5 = 삼진 아웃(0xa7c4c 가 넣음), 0xd = 그 밖의 아웃(0xa7d0c 가 넣음),
8·6·0xf 등 = 안타/진루 계열(0xa8098~0xa80ee 에서 따로 센다).

### 26·27 — **확정 (식) / 유력 (이벤트 목록이 플레이 단위로 비워진다는 점)**
```
a8096..a80f6: out = (이벤트 중 5 또는 0xd 의 개수)          ; [sp+0x30]
a8e58: if out == 2: if !state[0x1a]: 기록 26(더블플레이); 0xa755c(ctx,5)
a8e7a: if out == 3:                   기록 27(트리플플레이); 0xa755c(ctx,0)
(그리고 out>0 → 0xa599c(ctx,0x100), out>1 → 0xa599c(ctx,0x400) 플래그)
```
- 즉 "한 번의 정산에서 아웃 이벤트가 2개면 병살, 3개면 삼중살". state+0x1a 가 서 있으면 병살 기록만 막는다(0xb6c3c = `ldrb r0,[state,#0x1a]`, 뜻 미확인).
- 간이 엔진은 한 타석에 아웃을 1개만 만든다(3f 절) → **CPU 경기·동료 타석에서는 26·27 이 원리상 나오지 않는다.**
  사람이 수비하는 수비 시뮬레이션(주자 포스아웃·송구)이 여러 아웃을 한 플레이에 넣을 때만 나온다.
- 웹판: `gameRecords.ts` 에 26·27 판정이 없다(RALPH_PROGRESS "남은 것은 … 26·27"). 웹 타구 판정은 아웃 1개만 내므로 지금 구조로는 붙일 곳이 없다 —
  수비 시뮬레이션(5절)이 들어와야 한다. 넣는다면 "한 타석 결과로 늘어난 아웃 수 == 2 / == 3" 이 원본 식과 같은 의미다.

### 24 도루 저지 — **유력**

- +0x1d/+0x1e 는 0xc0fb4 가 득점 때 둘 다 1 로 세우는 칸이다(1d=득점/세이프, 1e=플레이 끝남으로 보임). "끝났는데 득점·세이프가 아닌 도루 주자" = 도루 실패 아웃.
- **간이 엔진에는 도루 실패가 없다.** 0xc1818(투구 판정 경로) 끝 0xc1982~0xc1ae2:

- 웹판: 간이 엔진(`quickAtBat.ts`·`simulateHalfInning.ts`)에 도루가 **아예 없다** — 원본은 CPU 경기에서도 위 규칙으로 도루해 주자를 민다.

## 1. 사용자 타구의 수비 시뮬레이션 — 뼈대만 **유력**, 수비수 이동·포구 식은 **미해결**

```
else                      → 6(안타)
```
- 화면 쪽 분기 0x51a8c → 점프표 0xd0488: 6·10 → 안타 이벤트 0xa5ffc, 8·12 → 홈런 이벤트 0xa5fec(글자 0xb), 11·13 → 아웃 0xa7d0c, 5 → 삼진 0xa7c4c.
  state[0x1e]=1 이면 담장을 넘어도 홈런이 아니라 안타로 가는 것으로 보아 **그라운드 룰 더블**(StrTIP[17] "바운드로 담장을 넘어가면 2루타")로 추정.
- 루타 수: 정산 0xa8024 가 **타자주자 객체(주자 목록 0번)의 루(+0x8c)** 를 읽는다(0xa8214~0xa8266, 플레이 중 아웃됐으면 −1). 2 → 2루타(선수 +0x24, 배너 8), 3 → 3루타(선수 +0x26, 기록 0 "3루타", 배너 9).

### 1e. 그라운드 홈런(장내 홈런) — **확정: 있다, 홈런으로 센다**
- 주자 목록 틱 갱신 0xaa0a8 (vtable 0xd8320): 주자가 홈(루 4)에 닿으면 득점 처리하고, 그 주자가 **이번 타석의 타자주자**(+0x98=1, 0xa93ac 가 추가할 때 세움)이고
  `state[0x1d]==0 && state[0xf]==0` 이면 `state[0x25] = 1` (0xaa1e2~0xaa1fe).
- 정산 0xa8024: `state[0x25]` 가 서 있으면 홈런 수 [sp+0x24] +1, 미션 칸 0xa57f8(R,4) = **R+0xcc 그라운드홈런 개수 +1** (a84cc~a84e8).
  이어서 홈런 경로(선수 홈런 +0x28, 0xa794c 연속 홈런, 득점 수로 기록 1~4 솔로/2점/3점/만루)를 그대로 탄다.
- 미션 목표 "그라운드홈런"(레코드 162 하위 4비트)은 0xaaa6c 가 이 R+0xcc 와 비교한다 (`ldr r1,[R+0xb4+0x18]`).
- 웹판 차이: `missionClearability`/RALPH 노트 "그라운드홈런은 추정: 장내 홈런이 없어 3루타로 센다" — **원본은 3루타가 아니라 홈런 + 그라운드홈런 둘 다로 센다.**
  웹 타구 근사(`battedBallOutcome.ts`)에는 장내 홈런을 만들 길이 없다.

### 1f. 미해결로 남긴 것
- 수비수가 공을 쫓는 목표점 선택, 포구 반경(cfg+0x42/0x44 = 17000×120/100 = 20400 을 거리 상한으로 쓰는 곳 0xa16a0 은 확인), 다이빙(필살수비) 발동 확률,
  주자 진루 판단(자동 주루)과 태그/포스 아웃 판정, state[0x80]/[0x20]/[0x1e]/[0x1f] 를 세우는 곳. 수비 AI 는 0xaf284·0xb1edc·0xb2c90·0xb3444·0xb3b38 (거리 함수를 부르는 곳들)에 있다.
