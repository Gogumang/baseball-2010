## 1. N4-1 — 일반·대전모드 "경기 시작" 조립 (`0x30f20` · `0x30be0`) — **확정**

### 1-0. 두 함수가 어느 모드인지 (확정)
호출자 `0x314b0` 안에서 **모드로 갈린다** (`0x31582`~`0x315a4`):
```
31582: r4 = this+0x13c ; r3 = [r4]          ; this+0x13c = 게임 모드 (H-modes: 전역 0x1552d14 와 같은 값)
31586: cmp r3, #1 ; bne 31590 → 3158c: bl 0x30f20(this)      ; 모드 1 = 일반모드
31590: r3 = [r4] − 8 ; cmp r3,#1 ; bhi 315a8
315a2: r1 = u8 [this+0x160]
315a4: bl 0x30be0(this, r1)                                   ; 모드 8·9 = 대전모드
```
- `0x30f20` ← `0x3158c`(0x314b0) · `0x31290`(0x311a8) — **일반모드 전용**.
- `0x30be0` ← `0x315a4` 한 곳뿐 — **대전모드 전용**. 둘째 인자 `u8 [this+0x160]` 이 0 이면 모드 **8**, 아니면 모드 **9** (`0x30bec`~`0x30bf8`). H-modes 2절의 "0x31dfe: 버퍼 플래그 0 이면 모드 8, 아니면 9" 와 같은 갈림이다.

> **Q3 정정 확인** — Q4 5-1 의 지적이 맞다. 이 둘은 메인메뉴 **그리기** 가 아니라 **경기 state 조립**이다.

### 1-1. 설정 레코드 `[this+0x120]+0xbc` 16바이트 — 칸 뜻 **확정**
J 1-2(채우는 쪽)와 여기(읽는 쪽)가 딱 맞물린다. 게다가 `howto.json[8]`("게임 진행 방법") 의
**1 유저 팀 → 2 AI 팀 → 3 선공/후공 → 4 구장 → 5 마투수 → 6 마타자** 순서와 그대로 대응한다.

| 칸 | 크기 | 뜻 | 읽는 곳 |
|---|---|---|---|
| `+0x0` | u32 | **유저(사람) 팀 번호** | `0x31014` → `0xb6bd4(state, rec[8], rec[0])` |
| `+0x4` | u32 | **AI(상대) 팀 번호** | `0x3102e` → `0xb6bd4(state, 1−rec[8], rec[4])` |
| `+0x8` | u32 | **사람이 맡는 측 (0 = 선공 / 1 = 후공)** | `0x30f44`·`0x30f50`(`r2 = 1 − rec[8]`) |
| `+0xc` | u8 | **구장 번호** | `0x310e2` → `state[0x30] = (s8)rec[0xc]` |
| `+0xd` | u8 | **마타자 id** (−1 = 없음) | `0x31046` → `0xb8870` |
| `+0xe` | u8 | **마투수 id** (−1 = 없음) | `0x31034` → `0xb88c8` |
| `+0xf` | u8 | 안 씀 | — |

### 1-2. 어느 쪽이 사람인가 · 선공/후공 — **확정**
`0x310a2`~`0x310e6` (일반모드):
```
310a2: state = [0x1552d0c] ; 0xb6814(state)          ; 경기 상태 초기화(S1·H-modes 확인)
310b8: state[1] = (u8)[this+0x13c]                    ; state+1 = 모드 바이트 (F-ui-layout 249행과 일치)
310be: 0xb6c18(state, rec[8],   0)                    ; state[0x31 + rec[8]]   = 0
310c8: 0xb6c18(state, 1−rec[8], 1)                    ; state[0x31 + (1−rec[8])] = 1
310d4: 0xb6bd4(state, rec[8],   rec[0])               ; state[0x28 + rec[8]]   = 유저 팀
310de: 0xb6bd4(state, 1−rec[8], rec[4])               ; state[0x28 + (1−rec[8])] = AI 팀
310e2: state[0x30] = (s8)rec[0xc]                     ; 구장
```
setter 실체(확정, `re dis`):
- `0xb6bd4(st, s, v)` = `strb v,[st+0x28+s]` · 읽기 `0xb6bdc(st,s)` = `s8 [st+0x28+s]` → **측별 팀 번호**
- `0xb6c18(st, s, v)` = `strb v,[st+0x31+s]` · 읽기 `0xb6c20(st,s)` = `s8 [st+0x31+s]` → **0 이면 그 측을 사람이 조작**(V5·J 41행·P1 263행과 같은 규약)

**측 0/1 의 뜻**: 초기화 `0xb6814` 가 `state[9] = 0`(공격 팀), `state[0xa] = 1`(수비 팀) 으로 시작한다(`0xb6836`·`0xb6886`).
즉 **측 0 = 1회 초에 공격 = 선공**, **측 1 = 후공(홈)**.
→ **`rec[8]` 는 "사람이 맡는 측" 이고, `rec[8] == 0` 이면 사람이 선공, `1` 이면 사람이 후공이다.** (빠른실행은 `bfa55(0,2)!=0 → 1`, 즉 반반)

### 1-3. 팀 레코드 두 개 `[this+0x140]`·`[this+0x144]` — 확정
`0x30fc2`~`0x31002`: `0x1238(0x29c)` 로 **0x29c 바이트** 객체 둘을 만들고 `0xae800` 으로 초기화해
`[this+0x140]`(측 0) · `[this+0x144]`(측 1) 에 넣는다. 접근은 늘 `[this+0x140 + 측*4]`.
```
31018: 0xb891c([this+0x140+rec[8]*4],     모드, rec[0], rec[8])      ; 사람 팀
31030: 0xb891c([this+0x140+(1−rec[8])*4], 모드, rec[4], 1−rec[8])    ; AI 팀
```
`0xb891c(tr, 모드, 팀번호, 슬롯)` (확정):
- `0x1400428(tr, 0, 0x290)` = 0 으로 지움 → `tr[0x24] = 모드`, `tr[0x25] = 팀번호`, `tr[0..0xd]`·`tr[0xe..0x23]` 0
- **모드 ∈ {1, 8, 9} 일 때만** `[tr+0x288] = 슬롯`
- `[tr+0x288]` 을 읽는 곳은 명부 공급자 `0xb8680(tr)` 뿐이다. `0xb8680` 은 `tr[0x24]`(모드)−1 로 점프표 **`0xd8a30`**(9칸)을 탄다:

| 모드 | 분기 | 하는 일 |
|---|---|---|
| 1 일반 | `0xb86d4` | `0x1f874(전역, [tr+0x288])` |
| 2 시즌 | `0xb869e` | `s8 tr[0x25]`(팀번호)로 |
| 3·4 나리 | `0xb86c6` | `0x1f988(전역, s8 tr[0x25])` |
| 5·6 미션 | `0xb86e2` | 아래 4절(U-27) 참조 |
| 7 홈런더비 | `0xb8728` | 기본(널) |
| 8 대전 | `0xb86aa` | `0x1f890(전역, [tr+0x288])` |
| 9 대전(도전/이벤트) | `0xb86b8` | `0x1f8a8(전역, [tr+0x288])` |

### 1-4. 마투수·마타자 배정 — **확정**
```
31034: 0xb88c8(사람팀, u8 rec[0xe])        ; 마투수 넣기  (0x1f824(전역,id) → 0xb521c, tr[0x26]++)
31046: 0xb8870(사람팀, u8 rec[0xd])        ; 마타자 넣기  (0x1f84c(전역,id) → 0xb53f0, tr[0x27]++)
31050: 0xb88c8(AI팀, 0x66968(u8 rec[0xe])) ; AI 마투수
31068: 0xb8870(AI팀, 0x66994(u8 rec[0xd])) ; AI 마타자
```
`0x66968`(마투수)·`0x66994`(마타자)는 **글자 하나까지 같은 함수**다(확정):
```
v = bfa54(0, 5)            ; 0..4 균등
if v == 내_id:  v = (v != 0) ? v−1 : 4
return v
```
→ **AI 쪽 마선수는 오픈 여부와 무관하게 0~4 중 무작위이고, 사람이 고른 것과만 겹치지 않는다.**
- ⚠️ **원본 버그성 동작(그대로 옮길 것)**: 인자가 `ldrb`(부호 없음)라 사람이 "없음"(−1 = 0xff)을 골라도
  `v == 0xff` 이 성립할 수 없다 → **사람이 마선수를 안 써도 AI 는 늘 마투수·마타자를 하나씩 얻는다.**
  (사람 쪽은 `0xb88c8` 안의 `0xb521c` 가 −1 을 돌려주면 건너뛴다 — `0xb88ec: adds r0,#1 ; beq`.)

### 1-4b. 선발 투수 무작위 지정 — **확정**
```
31088: 0xb8c94(AI팀,   0, bfa54(0,4))     ; 3107a~31084
3109e: 0xb8c94(사람팀, 0, bfa54(0,4))     ; 31090~3109c
```
`0xb8c94(tr, 0, k)` = `0xb5e98(명부, 0, k, 1)` = **로스터 투수 배열의 0번과 k번을 레코드째 맞바꾸기**
(R4 2a·P1 128·146 이 확정한 그 함수다. **투수 0번 = 선발**).
→ **일반·대전모드는 경기를 세울 때 양 팀 선발을 로스터 앞 4명 중 무작위로 고른다.** `bfa54(0,4)` 이므로 0~3 균등이고,
k=0 이 나오면 그대로다. 교환은 레코드째라 **영구**(P1 146 과 같은 성질).

### 1-6. 대전모드 `0x30be0` — 확정 (차이만)
1. 팀을 레코드가 아니라 **통신 슬롯**에서 읽는다: 모드 8 → `s16 [0x1f890(전역, 0/1) + 0]`, 모드 9 → `s16 [0x1f8a8(전역, 0/1) + 0]`.
   슬롯 0 = **내 팀(A)**, 슬롯 1 = **상대 팀(B)**.
2. 읽은 값을 **레코드에 되써 넣는다**(`0x30c86`~`0x30ca8`): `rec[0] = A`, `rec[4] = B`, **`rec[8] = 1`**, `rec[0xc] 의 최하위 바이트(구장) = A`.
   → **대전모드는 늘 내 쪽이 후공(측 1)** 이고 **구장은 내 팀 번호**다.
3. state 조립은 상수로 박혀 있다(`0x30d66`~`0x30da4`): `0xb6c18(st,1,0)`·`0xb6c18(st,0,1)`·`0xb6bd4(st,1,A)`·`0xb6bd4(st,0,B)`.
4. 팀 레코드도 같은 규약이다: `0xb891c([this+0x144], 모드, A, 0)` · `0xb891c([this+0x140], 모드, B, 1)` —
   여기서 넷째 인자는 **측이 아니라 통신 슬롯 번호**(1-3 의 `[tr+0x288]`). 측은 `[this+0x140 + 측*4]` 주소 쪽이 정한다.
   즉 `+0x144`(측 1) ← 슬롯 0(내 팀) ✓, `+0x140`(측 0) ← 슬롯 1(상대) ✓ — **어긋난 데가 없다.**
5. 마선수는 `+0x144`(내 쪽)가 레코드 값 그대로, `+0x140`(상대)가 `0x66968`/`0x66994` 무작위 — 일반모드와 같다.
6. 끝에서 `0x1fdb0(전역, 0x29/0x2a, …)` 로 슬롯이 **0x32·0x33 이 아니라 0x29·0x2a 계열**이다(`0x30dc0`~, 모드 8/9 로 또 갈림). 그 뒤는 안 팠다.

### 1-7. 빠른실행 "슬롯 굴림" — 덤으로 확정 (`0x311a8`)
Q4 가 "상태 22 갱신" 이라고 한 `0x311a8` 은 **빠른실행 연출 틱**이다:
```
311f0: if u8 [this+0x14c] == 0: return          ; 빠른실행 표시
311f6: if u8 [this+0xf4] == 0: return
31200: [this+0x134] = 0 ; [this+0x154] += 1
3121e: rec[0] = 0x9f5a0(전역) ; rec[4] = 0x9f5a0(전역)   ; 매 틱 팀만 다시 굴린다
31238: if [this+0x154] != 0x14(20): → 31296 (레코드에 팀만 써 넣고 끝)
3123c: rec[8] = (bfa54(0,2) != 0) ; rec[0xe] = 0x9f650(전역) ; rec[0xd] = 0x9f604(전역)
31290: [this+0xf4] = 0 ; bl 0x30f20(this)       ; 20틱째에 확정하고 경기를 세운다
```
→ **빠른실행은 팀만 20틱 동안 굴려 보이고, 선공/후공·마투수·마타자는 마지막 틱에 한 번 뽑는다.** (howto.json[8] 의 "(*) 키로 결정사항을 변경" 과 맞는다)

## 3. U-23 — 올해의 목표 표 `0xd7f9e` 를 읽는 줄 — **확정 (전수 부재 증명 포함)**

### 3-1. 표를 읽는 곳은 `0xa3de8` **하나뿐이다** — 확정
- `re xval 0xd7f9e` → `WORD 0xa3fd0 ← ldr 0xa3e28(함수 0xa3de8)` **1건**.
- `re xval 0xd7e9a`(투수 표) → `WORD 0xa3fd8 ← ldr 0xa3e78(함수 0xa3de8)` **1건**.
- 더해서 **리터럴 풀 전수 스캔**(`.text` 전체를 2바이트씩 훑어 값이 `0xd7d00..0xd8100` 인 워드를 모두 뽑음)을 돌렸다.
  그 범위에 든 워드 29개는 **전부 `0xa3390`~`0xa4f5c`**, 즉 `0xa3xxx`~`0xa4xxx` 시즌 평가 묶음 안에 있고,
  `0xd7f9e`·`0xd7e9a` 를 담은 것은 위 두 곳뿐이다. **표를 간접으로(다른 기준 주소 + 오프셋) 읽는 코드도 없다.**

### 3-2. 읽는 줄 자체 (`0xa3e20`~`0xa3e52`) — 확정

### 4-1. U-27 — 전역기록 `+0x11f` / `+0x176` 의 뜻 — **확정**

> **답: 이벤트 스크립트의 `match`(마선수 대결) 명령이 걸어 둔 "예약된 마선수 경기가 대기 중" 표시다.

```
8310a: if k == −1 → 이 줄은 건너뛴다 (빈 칸)
;; 소개 줄 (0x83110~0x83122)
       if k > 7 and 0x7b970(obj) == 0:  k += 0x10      ; 0x7b970(obj) = (obj[0x20] == 4) = 타자편
       [sp+0x38] = k
;; 효과 줄 (0x82ea2~0x82ec2)
       if k <= 7 or 타자편:  [sp+0x34] = k + 0x28      ; (곁들여 r7 = k + 0x37)
       else(투수편):         [sp+0x34] = k + 0x38      ; (곁들여 r7 = k + 0x47)
```
→ **소개 = `StrSKILL[k]`(투수편이고 k>7 이면 `StrSKILL[k+16]`) · 효과 = `StrSKILL[k+40]`(투수편이고 k>7 이면 `StrSKILL[k+56]`).**

### 7-4. 교차 검증 — 이식 저장소가 이미 같은 값을 쓴다
`tools/generate_game_data.py:267` 주석:
> `# 스킬 40종: 이름 StrCOMMON[55~94], 소개 StrSKILL[0~39], 효과 StrSKILL[40~79]`

**`+0x28` = 40 · `+0x38` = 56 = 40 + 16** 이 정확히 맞는다. 그리고 `src/shared/config/original/data/skills.json` 의 역할 배치가
**0~7 공통 · 8~23 타자(16개) · 24~39 투수(16개)** 라서 `k > 7 && 투수편 → k + 16` 이 **타자 스킬 번호를 그 짝인 투수 스킬로 옮기는 것**임이 확인된다
(예: 8 의외성 → 24 신선함 · 11 번트왕 → 27 닥터K · 13 좌완UP → 29 우타UP …).

### 7-5. 새 사실 (이식에 걸린다)
> **원본은 스킬을 "타자 번호(0~23)" 하나로만 들고 다니고, 투수편일 때만 읽을 때 +16 해서 투수 스킬로 바꾼다.**
> 즉 8~23 과 24~39 는 **같은 슬롯의 두 얼굴**이다.

- 이식 저장소는 `src/entities/career/model/playerCareer.ts:154-155` 가 `skillIds: readonly number[]` 를 **0~39 그대로** 들고 있다
  (주석: "가진 스킬 번호 (0~39, original/skills). 원본 보유 비트 +0x1b8").
  원본 비트가 24개(0~23)뿐인지 40개인지에 따라 **투수편 스킬 저장이 달라진다** — `+0x1b8` 비트 폭을 확인할 것.
  이 절의 읽는 쪽만으로는 "적어도 창은 0~23 기준 코드를 받는다" 까지만 확정이다(**저장 폭은 유력·미확인**).
- 화면 쪽: P6 3절이 이미 배치를 확정했으므로, `src/widgets/item-window`(P6 마지막 줄) 에 이 "효과 :" 줄만 더하면 된다.
