## 1. 기록연감 탭 막대의 박스 — **확정**

### 1-1. 박스는 PZX 프레임 안에 그대로 있다

`ui/slt_frame.pzx` 프레임 블록은 `u8 파트수 | u8 박스수 | 박스 × 8바이트(i16 x,y,w,h) | 파트…` 다.
기록연감이 쓰는 프레임 **4~8** 은 저마다 박스를 **하나씩** 달고 있다 (프레임 9 = 커서 그림, 박스 없음).

| 탭 | 프레임 (표 `0xcedcc`) | 박스 (x, y, w, h) |
|---|---|---|
| 0 기록 | 4 | **(2, 2, 72, 17)** |
| 1 진행 | 5 | **(31, 2, 72, 17)** |
| 2 스킬 | 6 | **(60, 2, 72, 17)** |
| 3 닉네임 | 7 | **(89, 2, 72, 17)** |
| 4 통계 | 8 | **(118, 2, 72, 17)** |

- **x 간격은 29** 다 (2 → 31 → 60 → 89 → 118). 막대 전체 폭 192 를 5 로 나눈 38.4 가 **아니다**.
- 고른 탭만 칸이 넓다(72). 안 고른 탭은 아이콘만 든 29px 칸이다. 프레임 파트를 보면 배치가 보인다 —
  안 고른 탭 i 의 x = `29i` (i < 고른탭), `29i + 46` (i > 고른탭), 고른 탭은 `29·고른탭` 에서 폭 75.
  (예: 프레임 6 = 탭 2 선택 → 안 고른 탭이 0, 29, 133, 162.)
- 박스 = 고른 탭의 글씨 칸이며 프레임 왼쪽 위를 원점으로 한다. 실제 화면 좌표는 **막대 x0 = 24** 를 더한다.

### 1-2. 쓰는 곳 (확정 — 0x2e29c 그리기 안)

박스 읽기 `0x94a65(out, sprite, 0, 0)` → 실제 알맹이는 **`0x94fe1`**:
`r6 = [sprite+0x18]`(현재 프레임의 박스 배열), 3번째 인자 0 이면 `offset = 박스번호 × 8`,
1 이면 `offset = (기준 + 박스번호) × 8`. 거기서 u8 두 개를 이어 붙여 i16 x, y, w, h 를 `out+0/2/4/6` 에 넣는다.
→ **박스 한 칸 = 8바이트 i16 x,y,w,h** 가 코드로도 확인된다.

그리기 순서 (`0x2e360`~`0x2e618`):

| 주소 | 하는 일 |
|---|---|
| 0x2e464 | `프레임 = 0xcedcc[탭]` (= 4 + 탭) |
| 0x2e474 | `0xba815(sp+0x148, slt_frame, 프레임, 1)` → 프레임 바깥 상자 (x,y,**w**,h) → sp+0x140 로 복사 |
| 0x2e4b6 | 막대 그리기 `0xba759(slt_frame, 프레임, x = W/2 − w/2 = 24, y = H/2 − 0x6c = **52**)` |
| 0x2e51c | `0x94a65(sp+0x138, slt_frame, 0, 0)` → **박스 0** → sp+0x138(x)/0x13a(y)/0x13c(w)/0x13e(h) |
| 0x2e546 | `0xba815(sp+0x130, img_text, 0xcedb8[탭] = 276+탭, 1)` → 탭 이름 그림 크기 (w = sp+0x134) |
| 0x2e568~0x2e5ba | 탭 이름 그리기 — `x = 24 + 박스x + (박스w − 이름w)/2`, `y = (H/2 − 0x6a = 54) + 박스y + 2` |
| 0x2e5ca~0x2e618 | 커서 **프레임 9** 그리기 — `x = 24 + 박스x`, `y = 54 + 박스y − 2` |

깜빡임: `[sp+0xa4] == 0` 이거나 `[sp+0xa8] != 0` 일 때만 커서를 그린다 (0x2e5be).

## 2. 도움말 — **확정** (표 0xcedf4 는 도움말 것이 아니었다)

### 2-1. 먼저 정정 — 상태 9·37 은 **랭킹**이다

`0x2524c`(상태 5·6·9 공용 하위 목록)가 고른 칸의 설명 글을 뽑는 자리 `0x25800~0x2584e` 는 상태별로 기준이 다르다:

| 상태 | 주소 | 설명 글 |
|---|---|---|
| 5 게임모드 | 0x25828 `adds r1, #6` | `StrMAINMENU[6 + 커서]` |
| 6 스페셜 | 0x2583a `adds r1, #0x10` | `StrMAINMENU[16 + 커서]` |
| **9** | **0x2584c `adds r1, #0x18`** | **`StrMAINMENU[24 + 커서]`** |

그리고 `StrMAINMENU[24]~[28]` 은

```
24 일반모드의!N순위를 확인합니다      27 대전모드의!N순위를 확인합니다
25 나만의 리그의!N순위를 확인합니다   28 훈련모드의!N순위를 확인합니다
26 시즌모드의!N순위를 확인합니다
```

→ **상태 9 = 랭킹 하위 메뉴**(일반·나리·시즌·대전·홈런더비 순위), **상태 37 = 랭킹 표 화면**이다.
최상위 바퀴 설명 `StrMAINMENU[0]~[5]` 도 이를 뒷받침한다 — `[2]` 가 도움말, `[4]` 가 "게임모드 별 랭킹과 자신의 현재 랭킹을 확인합니다" 로 따로 있다.
`0x28ad4`(상태 9 갱신) 가 `[메뉴+0xe6] = 커서` 를 넣고 다음 상태 `0x25 = 37` 로 가는 것도 확인했다(0x28b34~0x28b4a).

따라서 **표 `0xcedf4` = u8[5] `[9, 12, 15, 18, 20]` 은 랭킹 표 화면의 img_text 제목 프레임**이다
(`0x2fcf2`→`0x2fd18` 이 `memcpy(sp+0xc0, 0xcedf4, 5)`, `0x2fdfa` 가 `ldrsb [sp+0xc0 + [메뉴+0xe6]]`, 그 값으로 `0xba815(…, img_text, 값, 1)`).
그림을 직접 열어 확인했다 — img_text 프레임 **9 일반모드 · 12 나만의리그 · 15 시즌모드 · 18 대전모드 · 20 홈런더비**
(`base/sprites_v2/img_text/frames/009·012·015·018·020.png`). StrHOWTO 와는 아무 상관이 없다.

### 2-2. 진짜 도움말 — 상태 **7**, StrHOWTO 뷰어 객체 `0x63688`

- 그리기 `0x2fc8c`(상태 7·10 공용) = `0x58371(skin, 메뉴, 0)` + **`0x639a5(메뉴)`** + 머리띠 `0x54d95(메뉴, 0, 5)`.
  `0x639a5` 는 `0x58d10([뷰어+0x454])` 한 줄짜리 껍데기다.
- 갱신 `0x2cd54`(상태 7·10 공용) = `0x637d1(뷰어)` 가 참이면 다음 상태 4 + `0x639b9`(닫기).
- 뷰어를 만드는 곳은 두 군데뿐이다 (`0x63689` 리터럴 xref):
  | 부르는 곳 | 인자 | 뜻 |
  |---|---|---|
  | `0x2668c` (메인 메뉴) | 상태 ≠ 10 → `0x63689(뷰어, 0)` | **상태 7 = 도움말** |
  | `0x2668c` (메인 메뉴) | 상태 == 10 → `0x63689(뷰어, 6)` + `[뷰어+0xe6] = 6` + `[뷰어+0x45c] = 1` | **상태 10 = 게임문의** (장 하나 잠금) |
  | `0x3c25a` (경기 중 메뉴) | `movs r1, #0` → `0x63689(뷰어, 0)` | 경기 중 **[조작방법]** |
- I-controls 3절이 적은 "하위 4" 는 **경기 장면의 하위 상태 4**(0x3c322 `movs r3, #4`)이지 도움말 장 번호가 아니다.

### 2-3. 장(章) 표 `0xd0b18` — **확정**

`0x63688` 끝(0x63776~0x63794):

```
시작 = 0;  for (i = 0; i < 장번호; i++) 시작 += (s8)0xd0b18[i];
0x635d0(뷰어, 시작);          ; 첫 쪽 = StrHOWTO[시작]
[뷰어+0x45c] = 0;             ; 장 이동 잠금 해제 (상태 10 만 1 로 덮어씀)
```

`0xd0b18` (s8) = **`[5, 5, 7, 6, 3, 6, 4]`** — 합이 정확히 **36** 으로 StrHOWTO 의 항목 수와 같다.

| 장 | StrHOWTO 범위 | 내용 (howto.json 제목으로 확인) |
|---|---|---|
| 0 | [0]~[4] | **기본 조작** — 기본·타격·주루·투구·송구 조작 |
| 1 | [5]~[9] | 일반모드 |
| 2 | [10]~[16] | 나만의리그 |
| 3 | [17]~[22] | 시즌모드 |
| 4 | [23]~[25] | 대전모드 |
| 5 | [26]~[31] | **홈런더비·미션모드·스페셜·G포인트·환경설정(상세·데이터관리) 한 장** |
| 6 | [32]~[35] | **게임문의**(+빈 [33]·주의사항·제작진) — 상태 10 전용 |

- 장 넘기기는 `0x637d0` 안에서 같은 표를 다시 누적해 시작 항목을 다시 구한다(0x638c8·0x638e2·0x638f0·0x63926·0x63934).
  왼쪽 끝에서 되감을 때 `movs r4, #5`(0x638be), 오른쪽 끝 검사 `cmp r0, #4; bgt`(0x63914) →
  **메인 메뉴 도움말에서 돌아다닐 수 있는 장은 0~5 여섯 개**, 장 6 게임문의는 제 메뉴 칸에서만 열린다.

### 3-2. 답 — 기준점은 "공 잡기 **10틱 전**"

`d = 포구틱 − 현재틱 == 10` 이므로 카운터가 0 이 되는 순간은 **현재틱 = 포구틱 − 10** 이다.

```

             = 현재틱 (포구틱 − 10) ~ (포구틱 + 8)
```

즉 공이 손에 들어오기 **전부터** 반짝이기 시작해 잡고 나서 8틱까지 이어진다.

### 3-3. 원본 버그 — "19틱" 은 19**틱**이 아니라 19**번 호출**이다

카운터는 `0xb2648` 이 불릴 때마다 오른다. 한 틱짜리 갱신 `0x524c0` 이 같은 틱에 **두 함수를 잇달아** 부른다:

| `0x5241a` (`0x523bc` 안) | **반짝임 `경기+0x19ad` 가 켜져 있을 때만** 추가로 | +1 |

## 4. 주자 그림 — **확정**: 전용 그림판은 없다, 그림 객체만 따로다

### 4-1. 주자도 `defender.pzx` 를 쓴다

경기 장면 적재 `0x47cc8` 안 (0x48300~0x48394):

```

0x4831e  0x79a55([게임+0xf20], 팀, defender.pzx, defender.mpl)   ; ← 야수 그림 객체
0x48394  0x79cb5([게임+0xf24], 팀, defender.pzx, defender.mpl)   ; ← 주자 그림 객체
```

`0x79a54` 와 `0x79cb4` 는 글자 하나 다르지 않은 세터다 — `[obj+0x20] = 팀 · [obj+0xc] = 그림 · [obj+0x10] = 팔레트`.
→ **주자 전용 pzx 는 없다.** 그림 객체(0x30바이트, R3 7-1)만 야수용 `게임+0xf20` · 주자용 `게임+0xf24` 로 둘이다.

그리는 함수는 다르다 — 야수 `0x79b48`, 주자 **`0x79d10`**:

```
0x79d10(obj, 마선수쓰기, 프레임, 대상, dx, dy, …)
   마선수쓰기 ≠ 0 → 그림 = [obj+0x1c] (타자 마선수 그림)
   아니면       → 그림 = [obj+0xc], 팔레트 = [obj+0x10]
```
주자 그리기 `0x43a0c` 가 `마선수쓰기 = (주자+0x9c ≠ −1)` 로 준다(0x43aa8~0x43ab4).
야수 쪽 `0x79b48` 에 있던 "투수 마선수 +0x28" 갈래는 **주자에는 없다** — 주자는 +0x1c(타자 마선수)만 본다.

주자 그리기 자리: `0x46c88`(수비 화면 그리기)이 `0x43cb0` → `0x43278`(야수 9명) → **`0x43a0c`(주자)** 순으로 부른다.
주자 좌표는 월드→화면 `0xb94cd` 로 바꿔 그림 객체의 `+4`/`+8` 에 넣고 그린다.

### 4-2. 칸 배치는 야수와 **겹치지 않는다** — 야수 쪽에만 +17 이 붙는다

> ⚠️ 이 절은 8장(`+0x11`)을 푼 뒤 **고쳐 썼다**. 처음에는 "주자와 야수 달리기가 한 칸 어긋난 원본 버그" 라고 적었는데,

## 8. 그리기 플래그 `+0x11` — **정정: 좌우 반전이 아니라 "프레임 +17"**

### 8-1. 코드

야수 그리기 `0x79b48(obj, a, b, 프레임, 대상, dx, dy, …)`:

```
0x79b6e  r6 = 프레임 + 0x11
0x79b72  if (a != 0) r6 = 프레임          ; a = 투수 마선수 갈래
0x79b9e  str r6, [sp, #4]                 ; ← 0xbe8d5 의 "프레임" 자리
```
주자 그리기 `0x79d10` 의 같은 자리(0x79d40 `str r7, [sp, #4]`)에는 **프레임이 그대로** 들어간다.
두 함수가 `0xbe8d5` 에 넘기는 인자 배열이 한 칸도 다르지 않으므로, `[sp+4]` 는 **프레임 번호**다.
→ `+0x11` 은 뒤집기 비트가 아니라 **프레임에 더하는 17** 이다.

### 8-2. 에셋이 증명한다

| 그림 | 프레임 수 | +17 |
|---|---|---|
| `defender.pzx` (보통 수비수) | **125** | **더한다** (야수 17~86) |
| `ace/defender_medica·kao·roze·death·tiger` (타자 마선수) | **125** | **더한다** (`a == 0` 갈래) |
| `ace/defender_psyker·leony·bbmachine·ballantine·dragona` (투수 마선수) | **38** | **안 더한다** (`a != 0`) |

투수 마선수 그림에만 38장뿐인 이유가 여기서 풀린다 — 투수는 주자 칸(0~16)이 필요 없어서
**제 동작만 0부터 담았고**, 그래서 `a != 0` 일 때 17 을 더하지 않는다.
보통·타자 마선수 그림은 앞 17장이 주자 몫이라 야수는 17부터 쓴다.

### 8-3. 그럼 "효과 0x11" 은?

R6 3b 의 `효과 0x11`(b = 0 좌우 · 1 상하 · 2 둘 다)은 **PZX 파트 효과 번호**로, 이것과는 완전히 다른 값이다.
R6 3b 자체는 그대로 맞다. 틀린 것은 **R3 7-3 의 한 줄** — "a 가 아니면 그리기 플래그에 +0x11(좌우 반전 비트) 가 더해진다" 다.
이 함수에는 좌우 반전을 거는 자리가 아예 없다(좌/우 구분은 동작 3·4 가 **다른 프레임 묶음**으로 처리한다).

## 10. 금지 구역 확인

이 노트가 건드린 주소 가운데 **투구·타구 궤적 물리 루프(0xb3b38·0xb401c 계열, `docs/re/D-pitch-trajectory.md` · DECISIONS)** 에
