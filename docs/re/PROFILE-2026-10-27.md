## 한 줄 결론

- **React 는 병목이 아니다.**
  - 장면마다 커밋이 초당 17~33번이다. 게임 틱(16fps, 62ms)마다 1~2번 꼴이다.
  - 커밋 한 번의 렌더 시간은 0.13~0.33ms 다(데스크톱 ×1). 60초 동안 다 합쳐도 154~559ms, 주 스레드의 0.3~0.9% 다.
  - "값이 안 바뀌었는데 다시 그린" 렌더는 전체 렌더의 16~40% 다. 그러나 그 시간을 다 합쳐도 60초에 6~67ms 다.
- **틱 시계가 트리를 통째로 다시 그리는 것은 맞다.** 그래도 비용은 작다.
  - 경기 장면은 장면 루트(`TeamGameScene` · `PitcherGameScene` · `HomeRunDerbyScreen` · `MissionHud`)가 틱마다 상태를 올린다.
  - 그때 그 아래 컴포넌트의 50~90% 가 다시 렌더된다(커밋당 가운데 값 8~37개, p95 53~63개).
  - 그래도 DOM 은 거의 안 바뀐다. 타석 장면에서는 커밋이 있던 틀 1,164개 가운데 1,064개가 DOM 변경 0 이었다. 그림은 캔버스가 그린다.
- **가장 큰 낭비는 관리 화면의 공 무늬 바탕(`BallPatternBackdrop`)이다.**
  - 타일 `<img>` 약 200개가 틱마다 모두 `left` · `top` 을 바꾼다. 3틱마다 `src` 도 바꾼다.
  - 그래서 60초에 DOM 변경이 약 45만 건이다(틀당 약 125건).
  - 관리 · 시즌 관리 장면의 주 스레드는 ×4 에서 19~21% 바쁘다. 다른 장면은 10~13% 다.
- **틀은 어디서나 60fps 에 붙어 있다.**
  - 크로미움 아이폰 꼴 ×4: p95 16.7~16.8ms, p99 16.8ms. 긴 작업(>50ms)은 0개.
  - 웹킷 아이폰 꼴: p95 18ms, p99 18~19ms. 50ms 넘는 막힘은 0번. 웹킷은 CPU 늦추기가 없어서 ×1 이다.
- **Lighthouse(모바일)** 를 첫 화면(배포 빌드)에 돌렸다.
  - 점수: 성능 72~80 · 접근성 85 · 모범 사례 96 · SEO 82. TBT 0ms · CLS 0.
  - 성능을 깎는 것은 시뮬레이션 LCP 4.8~6.1초다.
  - 실제로 망과 CPU 를 늦춰서 재면(devtools 늦추기) LCP 는 **1.8초**다. 시뮬레이션은 첫 화면 뒤의 미리 받기 449건을 LCP 길로 함께 셈해서 크게 나온다.
  - 지적의 대부분은 게임 특성상 해당 없음이거나 호스팅 설정이다(4-3절).

### 1-1. 잰 방법

## 2. CPU 프로파일 (크롬 Performance)

### 2-1. 잰 방법

- **빌드**: 압축 끈 e2e 빌드(`vite build --mode e2e --minify false`)다. rolldown 이 남긴 `//#region <원본 경로>` 표시로 샘플을 원본 파일에 붙였다.
- **환경**: Playwright 크로미움, 아이폰 13 꼴(모바일 · 터치 · 390×664)에 CDP `Emulation.setCPUThrottlingRate(4)` 를 걸었다.
- **재기**: CDP `Profiler`(간격 250µs)를 장면마다 30초 놀며 켰다. 놀이는 1절과 같다. `Performance.getMetrics` 로 스타일 · 레이아웃 시간도 쟀다.
- **갈래 나누기**:

| 갈래 | 들어가는 것 |
|---|---|
| 렌더(React) | `react-dom` · `react/jsx-runtime` · scheduler |
| 렌더(컴포넌트) | `.tsx` · `ui/` 의 함수 |
| 렌더(DOM) | 내장 `setAttribute` · `appendChild` · `removeChild` 따위 |
| 그리기 | `canvas` · `sprite` · `pixelEffect` · `screen565` · `particles` 경로, 또는 이름이 draw · compose · palette 따위인 함수, 그리고 캔버스 내장(`getImageData` · `drawImage` · `getContext` …) |
| 진행 로직 | 나머지 `src` |
| GC | `(garbage collector)` |
| 브라우저 내부 | `(program)`: 스타일 · 레이아웃 · 페인트 · 합성 · 이미지 디코드 · 작업 틀 |

## 3. 틀 시간 · 긴 작업

30초씩 놀며 쟀다. 틀 간격은 rAF 시각 차이다. 긴 작업은 크로미움 `PerformanceObserver('longtask')` 로 잡았다. 두 브라우저 모두 setTimeout 고리로 50ms 넘는 막힘도 쟀다.

| 장면 | 크로미움 아이폰 꼴 ×4: p50 / p95 / p99 | 긴 작업 | 웹킷 아이폰 꼴 ×1: p50 / p95 / p99 / 최대 | >50ms 막힘 |
|---|---|---:|---|---:|
| 타석 | 16.7 / 16.7 / 16.8ms | 0 | 17 / 18 / 18 / 21ms | 0 |
| 투구 | 16.7 / 16.7 / 16.8ms | 0 | 17 / 18 / 18 / 26ms | 0 |
| 수비 판 | 16.7 / 16.7 / 16.8ms | 0 | 17 / 18 / 18 / 23ms | 0 |
| 관리 메뉴 | 16.7 / 16.8 / 16.8ms | 0 | 17 / 18 / 18 / 20ms | 0 |
| 시즌 관리 | 16.7 / 16.7 / 16.8ms | 0 | 17 / 18 / 18 / 21ms | 0 |
| 홈런더비 | 16.7 / 16.8 / 16.8ms | 0 | 17 / 18 / 19 / 44ms | 0 |
| 미션 | 16.7 / 16.7 / 16.8ms | 0 | 17 / 18 / 18 / 28ms | 0 |

- 크로미움 ×4 는 판마다 250~333ms 틈이 한 번 있었다. CPU 늦추기를 켠 순간이다.
  - 긴 작업 감시와 막힘 탐침이 둘 다 0 이었으니 주 스레드가 막힌 것이 아니다.
- 웹킷은 타이머가 1ms 단위로 잘려서 17 · 18 로 나온다.
- 웹킷에는 CPU 늦추기가 없다(Playwright webkit 에 CDP 가 없다). 그래서 "아이폰 ×4" 는 크로미움 아이폰 꼴로 대신 쟀다.

## 4. Lighthouse

### 4-1. 잰 방법

- **판**: Lighthouse 13.5.0(2026-09-18 판)이다.
  - 프로젝트 dev 의존성에는 없었다. 지시대로 `npx` 는 쓰지 않았다. 프로젝트 dev 의존성으로 잠깐 넣었다가 다 재고 뺐다(6절).
- **실행**: `lighthouse <url> --output=json --output=html --chrome-flags="--headless=new"` 를 기본 모바일 설정으로 돌렸다.
  - 기본 모바일 설정은 Moto G 꼴 화면, 시뮬레이션 늦추기(왕복 150ms · 1.6Mbps), CPU ×4 다.
  - 크롬은 설치된 Google Chrome 이다(`CHROME_PATH`).
- **대상**:
  - 첫 화면은 배포 빌드(`vite build`, `base: './'`)를 `vite preview` 로 띄웠다. 두 번 돌렸다.
  - 장면은 압축 켠 e2e 빌드의 `?scene=nari-management` · `?scene=general-bat` 이다. 바로가기는 배포 빌드에 없어서 e2e 빌드를 썼다.
    - 장면 바로가기는 픽스처를 깔고, 모드 화면 덩이를 다 받고, 단계를 밟는다. 사람 길보다 무겁다.
    - 그래서 장면 점수는 참고값이다.

## 7. 할 가치가 없는 것과 그 까닭

- **틱 타이머 하나로 묶어 커밋 합치기** (투구 · 수비 판에서 틀당 커밋 2~6번).
  - 커밋 하나가 0.2ms 안팎이다. 합쳐도 ×4 에서 틀당 1ms 를 못 줄인다.
  - 부르는 차례가 바뀌면 틱 콜백 안의 굴림(효과음 · 굴림 · 파티클) 차례가 바뀔 수 있다. 난수 위험이 이득보다 크다.
- **장면 루트 아래를 memo · context 쪼개기로 나눠 "트리 통째 다시 그리기" 줄이기.**
  - 다시 그려도 DOM 이 거의 안 바뀌고, 렌더 합이 60초에 0.15~0.56초다(데스크톱).
  - 원본 루프 구조(틱마다 갱신 · 그리기)를 흐트러뜨려 틱 정렬(10-24 결정 "틱 시계 하나로")을 깰 위험이 있다.
- **react-dom 바꾸기(Preact 따위) · React 19 올리기.** 렌더 몫이 바쁜 시간의 7~23% 이고, 그 바쁜 시간이 주 스레드의 10~20% 다. 얻을 것이 바쁜 시간의 몇 %뿐이다.
- **하늘 조명 `getImageData` · `composeRgba` 기억해 두기** (r306 B2).
  - 타석 · 투구 그리기의 가장 큰 몫이다. 그래도 ×4 에서 30초에 0.5~0.8초, 틀당 0.3~0.4ms 다.
  - 열쇠를 놓치면 픽셀이 다르다. 여전히 보류.
- **`getContext` · `effectContextOf` · `sameDrawInput` 다듬기.** 7장면 합쳐 ×4 에서 210초에 0.6초(0.3%)다. 부르는 곳이 넓어서 고칠 거리에 비해 이득이 없다.
- **GC 줄이기.** 어디서나 바쁜 시간의 1~2% 다.
- **AudioContext 미리 만들기 · 늦추기.**
  - 이미 첫 소리 때 만든다. ×4 에서 115~121ms 는 진입 때 한 번뿐이다.
  - 소리 여는 때가 바뀌면 자동 재생 제약 쪽 동작이 달라질 수 있다.
- **Lighthouse 지적 가운데 게임 특성인 것.** `user-scalable=no` · 원본 빨강 글자 대비 · 원본 터치 칸 크기 · 스프라이트 크기 표시 · 모드 덩이 미리 받기 · agentic-browsing. 4-3절 표 참고. 고치면 원본과 달라지거나 이득이 없다.

## 8. 잰 방법 (다시 잴 때)

측정 스크립트는 저장소에 남기지 않았다. 아래는 다시 만들 때의 뼈대다.

- **프로파일링 빌드**: 임시 설정 파일 하나를 만든다.

  ```ts
  // vite.profile.config.ts (임시, 커밋하지 않는다)
  import { defineConfig, mergeConfig } from 'vite'
  import base from './vite.config'
  export default mergeConfig(base, defineConfig({
    resolve: { alias: [{ find: /^react-dom$/, replacement: 'react-dom/profiling' }] },
    build: { minify: false },
  }))
  ```

  - 빌드: `yarn vite build --config vite.profile.config.ts --mode e2e --outDir <임시>`.
  - 띄우기: `vite preview --outDir <임시> --port 58xx`.
  - 배포 빌드는 `react-dom` 프로덕션 판 그대로다. 별칭은 이 설정 파일에만 있다.
- **커밋 집계**: Playwright `page.addInitScript` 로 `__REACT_DEVTOOLS_GLOBAL_HOOK__` 을 달고, `onCommitFiberRoot(id, root)` 에서 섬유를 돈다(1-1절의 판정).
  - React 18 프로덕션 · 프로파일링 판 모두 이 훅을 부른다.
  - `actualDuration` 은 프로파일링 판에만 있다.
