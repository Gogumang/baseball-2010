# R15 — 경기 화면 0x51408 이 쓰는 함수 포인터 0xac758 의 정체

## 체크리스트
- [x] 0. 선행 노트 읽기 (R10-game-states, R8-record-triggers, R3-field-view, I-controls)
- [x] 1. 0xac758 이 무엇인지 (함수 시작인가 / 데이터인가), 0x51408 에서 어떻게 쓰이는지
- [x] 2. 0xac758 함수 본문 디스어셈 — 인자·반환값
- [x] 3. 0xac758 을 부르는 조건 (0x51408 내부 분기)
- [x] 4. 게임 규칙 영향 판정 + 웹판 대응 위치
- [x] 5. (추가) I-controls: 필살송구 아웃이 어느 선수/팀에 붙는지 (0xa77f0 내부)
- [x] 6. (추가) I-controls: 작은 지도(0x395f4) 점 모양
- [-] 7. (추가) I-controls: 수비수 동작 0x78 을 세우는 곳
- [x] 8. (추가) R10: 상태 0x20 진입 경로
- [x] 9. (추가) R10: 0x13 의 +0x199a 플래그
- [x] 10. (추가) R8: ctx+0x24 (자동진행 플래그) 확인
- [x] 11. (추가) R8: state[0x88]·state[0x89] 이름

## 요약
주제 **0xac758** 은 풀렸다: 타격 순간 스윙 타이밍 점수(0~100)를 1/2/3 등급으로 자르는 3줄짜리 함수이고, 등급은 메시지 0xbc5 로 경기 장면에 가서 **진동 100/200/300 ms** 로만 쓰인다. 게임 규칙 영향 0, 웹판은 진동 자체가 없다. Q0 가 "CPU 교체/작전 계열로 보임" 이라 적은 0xac758~0xacb20(0x3c8) 추정은 틀렸다(함수는 0x3c 바이트).

덤으로 맡은 7건 중 **5건 확정, 1건 부정 증거로 닫음, 1건 미해결**:
- (5) 필살송구 아웃(기록 36)은 **어느 선수에도 안 붙는다** — 세이브 누계 cnt[36]·그 경기 G 누계뿐, 게이트만 "사람이 수비 중" (확정).
- (6) 작은 지도: 테두리 두 겹(색 확정, `0x1400748` 은 빨강이 아니라 `setColor` 스텁 — R3 정정) + **주자 점은 색칠이 아니라 game_ui 그림 한 장을 중심 정렬**. 그림 번호만 미해결.
- (7) 수비수 동작 `0x78`: 세우는 곳이 **바이너리 전체에 없다**(상수 전수 검색). 읽는 쪽에서 프레임 14 = **동작 5 의 세 번째 포즈 고정**. 죽은 갈래로 본다.
- (8) 경기 상태 `0x20`: **들어가는 길 없음**(예약 0곳·메시지 0 인자 0곳·계산되는 인자 전부 추적). 표에는 0x19(경기 끝)와 같은 칸이 있는 쌍둥이 번호다. 덤: **메시지 0 = 상태 바꾸기(인자가 곧 상태 번호)** 를 확정.
- (9) `+0x199a` = **"홈런성(결과 24~26) · 담장/폴 미접촉 · 낙구거리 > 111" 인 큰 타구 감상 플래그**. 같은 판정 0x392ac 이 타구음 7·"!" 효과·상태 0x13 대기를 한꺼번에 고른다 (확정).
- (10) `ctx+0x24` 첫 바이트 = **"사람 투수가 강판되어 남은 경기를 간이 엔진이 돌리는 중"**. R8 의 "30G 자동진행" 해석은 **틀렸다** — 30G 자동진행은 `engine+0xa0` 이고 첫 바이트는 0 인 채다(정정).
- (11) `state[0x88]` = **출루 허용**(정산 뒤 살아 있는 주자), `state[0x89]` = **피안타**. 둘 다 수비 팀이 사람일 때만, 0xa8024 안 한 곳씩 (확정).

남은 것: 작은 지도 점의 game_ui 그림 번호(구조체 +0x54 고정 경로라 코드로는 못 읽음 — 그림을 렌더해 눈으로 맞춰야 한다), 동작 0x78 을 표에서 꺼내 넘기는 경로가 있을 가능성(배제 못 함).

## 1~4. 0xac758 = 타격 타이밍 → 진동 세기 등급 (확정)

### 결론 한 줄
`0xac758` 은 **타격 순간 스윙 타이밍 점수(0~100)를 1/2/3 세 등급으로 자르는 3줄짜리 함수**다.
그 등급은 경기 장면에 메시지 `0xbc5` 로 전달되고, 받는 쪽은 **진동을 100 / 200 / 300 ms** 울린다.
**게임 규칙(판정·기록·확률)에는 전혀 영향이 없다 — 순수 햅틱 연출.**

### 4-1. 부르는 자리 (확정)
타구가 맞은 직후(메시지 0x11·0x13 을 보낸 뒤, R10 의 "맞았다" 가지) 타구음 선택이 끝나면 바로 이어진다.

```
000515b8: adds r5, r7, #0 ; adds r5, #0x70      ; r5 = 경기+0x70 (= 0x509a0 이 받는 장면 객체)
000515bc: → 0xbfbac(r5, 0x11, 0, [sp+0x50])     ; 메시지 0x11
000515ca: → 0xbfbac(r5, 0, 0x13, 0)             ; 메시지 0x13
000515d6: ldr r2,[sp,#0x64] ; ldrb r3,[r2] ; cmp #0 ; beq 0x5164c   ; 0 이면 타구음만 건너뜀
   (타구음 고르기: 0x392ac→7 / [[sp+0x84]][8]≠0→9 / 0x35988→5 / 0x39304→59 아니면 6)
0005164c: adds r0, r7, #0
0005164e: bl   #0x34be0                          ; t = 스윙 타이밍 점수 0..100
00051652: ldr  r6, [sp, #0x74]
00051654: adds r1, r0, #0                        ; 인자2 = t
00051656: ldr  r3, =0xac759
00051658: ldr  r0, [r6]                          ; 인자1 (쓰이지 않음)
0005165a: bl   #0xca9f8                          ; = bx r3  → 0xac758(r0, t)
0005165e: ldr  r1, =0xbc5
00051660: adds r2, r0, #0                        ; 인자 = 등급 1/2/3
00051664: adds r0, r5, #0
00051666: ldr  r4, =0xbfbad
00051668: bl   #0xca9fc                          ; 0xbfbac(경기+0x70, 0xbc5, 등급, 0) = 메시지 큐잉
```
- `0xca9f0/f4/f8/fc/a00/a04` 는 각각 `bx r1/r2/r3/r4/r5/r6` 짜리 2바이트 트램폴린이다 → `bl 0xca9f8` = **r3 로 간접 호출**.
- **부르는 조건: 배트에 공이 맞은 모든 타구.** `[sp+0x64]` 바이트가 0 이어도(=타구음 생략) 이 호출은 그대로 탄다. 헛스윙·볼 쪽(0x4e26e → 상태 0x12)은 여기로 오지 않는다.

### 4-2. 함수 본문 (확정) — 0xac758, 0x3c 바이트(0xac792 에서 끝, 0xac794~0xac79a 는 리터럴 풀)
```
000ac758: push {r4,r5,r6,lr}
000ac75a: ldr  r3, =0x14000c0        ; D = d_level.dat 객체
000ac75c: ldr  r6, =0xca7b5          ; __divsi3 (0xca7b4)
000ac75e: ldr  r3, [r3]
000ac760: movs r0,#0x12 ; ldrsh r2,[r3,r0]   ; hi = (s16)D[0x12]
000ac764: movs r0,#0x10 ; ldrsh r3,[r3,r0]   ; lo = (s16)D[0x10]
000ac768: subs r4, r2, r3            ; span = hi - lo
000ac76a: subs r5, r1, r3            ; v    = t  - lo
000ac76c: r0=span, r1=3 ; bl 0xcaa04 ; = bx r6 = div(span,3)
000ac774: cmp r5,r0 ; blt → ...      ; v >= span/3  → return 3
000ac77c: r0=-span, r1=3 ; div(-span,3)
000ac784: cmp r5,r0 ; bgt → 2        ; v <= -span/3 → return 1, 아니면 return 2
000ac78e: pop {r4,r5,r6} ; pop {r1} ; bx r1
```
- **인자**: `r0` = **쓰이지 않음**(0xac760 에서 곧바로 덮어씀). 실제 인자는 `r1` = 타이밍 점수 t 하나뿐.
- **반환값**: `int` 1 / 2 / 3.
- `0xca7b4` 는 `cmp r1,#0 / beq ... / eors r4,r1(부호)` 로 시작하는 **부호 있는 나눗셈(__divsi3)** 이다.

### 4-3. 상수 값 (확정)
`0x14000c0` = **d_level.dat 객체**(객체오프셋 = 파일오프셋 + 4, H2 노트 규칙). `base/work/jar/data/d_level.dat` 앞부분:
```
00000000: 4000 0000 6e00 1e00 0600 0400 0000 6400
00000010: 2c01 0700 dc00 ac03 4600 5000 0300 0600
```
- `D[0x10]` = 파일 0x0c = **0**  (= 타이밍 점수 하한)
- `D[0x12]` = 파일 0x0e = **100** (= 타이밍 점수 상한)

→ span = 100, span/3 = 33.
```
grade(t) = 3  if t >= 33
         = 1  if t <= -33
         = 2  otherwise
```

### 4-4. t 는 어디서 오나 — 0x34be0 (스윙 타이밍 점수, 기존 Q1/H2 노트 보강)
`0x34be0(경기)` 의 마지막 두 줄이 **`D[0x10]` 으로 하한 클램프**한다:
```
00034c50: ldr r3,=0x14000c0 ; ldr r3,[r3] ; movs r1,#0x10 ; ldrsh r3,[r3,r1]
00034c58: cmp r0,r3 ; bge 0x34c5e ; adds r0,r3,#0      ; t = max(t, D[0x10]=0)
```
그리고 최대값 쪽 배율이 `D[0x12]`(=100) 이다.
- 보통 구질: `d = F − (N−2)`, `t = 100 · (24 − 100|d|/(N−1)) / 24`, 하한 0. (N ≤ 2 면 0 반환)
- 구질 0x16(마구): `t = 100 · (22 − 100|d|/12) / 22`, 하한 0. → 창이 좁다(H2 3-5 와 일치).

**따라서 t ∈ [0,100] 이라 등급 1(=100ms)은 실제로는 나오지 않는다.** 코드상 갈래만 남아 있다(원본 데이터 기준, d_level.dat 의 0x0c 가 음수였다면 살아났을 가지).
실효 동작: **타이밍 33 이상 → 300 ms, 그 미만 → 200 ms.**

### 4-5. 받는 쪽 — 메시지 0xbc5 (확정)
`0x509a0`(경기 장면 vtable 슬롯 12) 의 메시지 if-체인. 이 함수는 2KB 를 넘어서 **`bl` 을 긴 분기로 쓴다**(0x523aa 는 `add sp,#0xf4 / pop / bx r1` 로 끝나는 **에필로그**, 반환값 2).
```
00050bcc: ldr r3,=0xbc5 ; cmp r2,r3 ; bne +2 ; bl #0x5228c     ; 0xbc5 → 0x5228c
00050bd6: adds r3,#1    ; cmp r2,r3 ; bne +2 ; bl #0x522c8     ; 0xbc6 → 0x522c8
```
`0x5228c` = 인자(= [sp+0xec] = 등급) 스위치:
```
0005228c: ldr r3,[sp,#0xec]
  r3==2 → 0x522b0 : r0=0xc8(200), r1=0x64 → 0x3a44
  r3==1 → 0x522bc : r0=0x64(100), r1=0x64 → 0x3a44
  r3==3 → 0x522a2 : r0=0x96<<1(300), r1=0x64 → 0x3a44
  그 밖 → 에필로그
```
`0x3a44 = vibrate(ms, level)` — L 노트 1-E 에서 확정된 진동 함수(저장데이터 +0x3b "진동 켬" 일 때만 `0x6e538(snd, ms, 100)`).
→ **등급 1/2/3 = 진동 100/200/300 ms.**

덤으로 `0xbc6` (0x522c8): `경기+0x19ad` 바이트를 0 으로 지운다(진동과 무관한 플래그 해제).

### 4-6. 규칙 영향 / 웹판 (확정)
- **게임 규칙 영향 없음.** 반환값은 `0x3a44` 진동 길이에만 쓰이고, 어떤 판정·기록·난수에도 들어가지 않는다. 안타/아웃 판정은 이미 `0xab214`(H2·Q1) 에서 끝난 뒤다.
- 웹판: `navigator.vibrate` 참조 0건 (`/usr/bin/grep -rn vibrate src/` → 없음). 즉 이 계열 전체가 미구현이며, **구현할 필요도 낮다**(연출만).
- Q0 감사표의 "0xac758~0xacb20 (0x3c8) — CPU 교체/작전 계열로 보임(짐작)" 은 **틀렸다**. 0xac758 함수 자체는 **0x3c 바이트**(0xac758~0xac792 + 리터럴 0xac794~0xac79b)이고, 0xac79c 부터는 별개의 작은 함수들(0xac79c·0xac7a4·0xac7ac·0xac7b0·0xac7b4 …)이다. 교체/작전과 무관.

## 5. 필살송구 아웃(기록 36)은 누구 몫인가 — 확정 (R3 21행 미해결 해소)

**답: 어느 "선수" 에도 안 붙는다. 선수 성적·팀 성적에는 전혀 기록되지 않고, 세이브 파일의 "기록달성" 누계 한 칸(cnt[36])과 그 경기 G 누계에만 붙는다.**

0xa77f0 의 집계 구간을 직접 봤다 — 쓰는 곳이 네 군데뿐이고 선수 구조체는 건드리지 않는다:
```
000a78e2: ldrb r3,[r0,r4] ; adds r3,#1 ; strb r3,[r0,r4]   ; ctx+0x170 쪽 이번 경기 카운트[k]++
000a78e8: ldr  r2,[r5,#0x28] ; ldrb r3,[r2,r4]             ; 세이브 누계 cnt[k]
000a78ec:   0..255 클램프 후 strb r3,[r2,r4]               ; 누계[k] = min(누계+1, 255)
000a78fc: r0 = [ctx+0x180] ; [r0] += u32 0xd8158[k]        ; 이번 경기 G 누계 += G표[k]
000a790c: sp+1 = k ; 0xa91fc(ctx+0x170, &k)                ; 화면 알림 큐
000a7922: 0x62234([0x1552cfc], k)                          ; 해금 검사
```
- "팀" 은 **게이트로만** 들어간다: `k == 36` 은 `state[0x31 + state[0xa]] == 0`(= **수비 팀이 사람**) 가지에서만 통과한다(R8 1절). 즉 **사람이 수비 중일 때만** 들어오고, 사람 팀/상대 팀 어느 쪽 기록란에도 적히지 않는다.
- 실제로 아웃을 만든 야수가 누군지도 안 본다. R3 3-2 대로 지급 지점은 플레이 정산 `0xa8024` 안 `0xa810a` 한 곳이고, "레이저 송구가 발동한 플레이에서 아웃이 하나라도 났으면" 이 조건이다.
- 웹판 대응: `src/**/gameRecords.ts` 의 기록 36. 원본과 같은 "선수 무관, 사람 수비 한정" 이어야 맞다.

## 6. 작은 지도(0x395f4) 점 모양 — 확정(그리는 방식) / 어느 그림인지 미해결

`0x395f4(this=경기장면, x0, y0)`. `this+0x1e8` 객체의 바이트 `+5 == 1` (지도 켜짐/큰 모드로 보임) 일 때만 테두리를 그린다.

### 6-1. 틀 (확정)
```
0x39644: r = [game_ui+0xc→+8→+0x24].vt1c(x0, y0, &r, 0, 0)   ; 지도 바탕 그림을 그리고 상자 r 을 돌려받음
0x3965a: r.x -= 2 ; r.y -= 2 ; r.w += 4 ; r.h += 4
0x39680: setColor(0x18,0x29,0x45)  ; 0x1400748 = WIPI 색 지정 스텁
0x396a4: fillRect(r.x, r.y, r.w, r.h)          ; 0x6a9f0 = 채우기, [0x1400070] 그래픽스
0x396a8: setColor(0x5a,0x6b,0x7d)
0x396d0: fillRect(r.x+1, r.y+1, r.w-2, r.h-2)
0x396f4: fillRect(r.x+2, r.y+2, r.w-4, r.h-4)   ; 세 번째는 색 인자 0
```
- **R3 1-4 정정**: `0x1400748` 은 "빨강" 이 아니라 **`setColor(r,g,b)` WIPI API 스텁**이다(0x1400538 진동 스텁과 같은 16바이트 꼴). 색은 **바깥 테 (0x18,0x29,0x45) 짙은 남색 + 안쪽 테 (0x5a,0x6b,0x7d) 청회색** 두 겹뿐이다.

### 6-2. 투수판과 주자 점 (확정 — 모양 빼고)
```
0x39728: 0xb9480(sp+0x30, [this+0x3f0], [0xcfa8c], [0xcfa8c+8])  ; 투수판 월드좌표 투영
0x39746: n = 0xa9598(주자관리)                    ; 주자 수
0x39754: 루프 i<n:  p = 0xa9564(주자관리, i)
0x39762:   if  (주자 p + 0x78 + 0x1e) 바이트 != 0 → 건너뜀   ; (0x96 = 아웃 표시 계열로 보임 — 유력)
0x3976c:   월드좌표 12바이트 = p+0x20 ~ p+0x2b 복사
0x39790:   0xb94cc(sp+0x58, 배율, 좌표…)          ; → 지도 칸 좌표
0x39796:   x = x0 + px - (투수판 px) + 1
           y = y0 + py - (투수판 py) + 4
0x397be:   x -= img.vt1c()/2 ; y -= img.vt20()/2  ; 그림 폭·높이의 절반만큼 당겨 **중심 정렬**
0x397f0:   img.vt14(x, y, 1, 0xc, 0)              ; 그리기 (bl 0xcaa1c = bx ip)
```
- **점은 색 찍기가 아니라 그림(스프라이트) 한 장**이다. 그래서 "모양" 은 `ui/game_ui.pzx` 안 그림 한 칸이고, 코드가 하는 일은 **월드좌표를 지도 칸으로 줄이고 그림 중심을 그 자리에 맞추는 것**뿐이다.
- 그림 객체는 `[[[scene+0x1018] + 8] + 8] + 0x54` 로 고정 경로를 타고 온다. 여기 쓰이는 vtable 슬롯은 `0x14`(그리기)·`0x1c`(폭)·`0x20`(높이).
- **미해결**: 그 `+0x54` 칸이 game_ui 의 몇 번 그림인지. 다른 곳들(0x42e3a 등)은 `0xba814(상자, 스프라이트, 그림번호, 0)` 로 **번호를 인자로** 넘기는데 여기만 구조체를 직접 파고들어서, 번호를 코드에서 못 읽는다. 그림 파일을 렌더해 눈으로 맞추는 쪽이 빠르다.
- 투수판은 기준점 역할만 한다(모든 주자 좌표를 투수판 기준 상대좌표로 만든다).

## 7. 수비수 동작 `0x78` 을 세우는 곳 — 미해결(강한 정황: **아무 데서도 안 세운다**)

### 7-1. 먼저 확정된 것 — 동작을 세우는 유일한 통로
```
000a1234: push {lr}                 ; setAction(야수 obj, a)  — 야수 vtable 0xd7934 의 슬롯 0x44 (= 0xd7978)
000a1236: adds r2, r0, #0 ; adds r2, #0xa8
000a123a: ldr  r3, [r2] ; cmp r3, r1 ; beq 0xa1248     ; 같은 동작이면 아무것도 안 함
000a1240: str  r1, [r2]            ; 야수+0xa8 = a
000a1242: movs r3,#0 ; adds r2,#4 ; str r3,[r2]        ; 야수+0xac(경과 t) = 0
000a1248: pop {r0} ; bx r0
```
- `re xref 0xa1234` → **직접 BL 호출 0건**, 참조는 vtable 칸 `0xd7978` 하나뿐. 즉 동작 바꾸기는 전부 `야수.vt44(a)` 로만 일어난다.
- `야수+0xa8` 에 직접 `str` 하는 곳은 이 함수뿐이다(0xa0000~0xa4000 구간 `adds r?,#0xa8` 전수 확인).

### 7-2. 0x78 을 넘기는 자리를 못 찾았다
바이너리 전체에서 상수 0x78 이 나오는 자리를 모두 훑었다:
- `movs rN, #0x78` 24곳 — 야수 코드 안은 `0xa16b0`(거리 ×120/100, 필살송구 상한)·`0xa35de`(×120)·`0xa3214`·`0xa3236`(구조체 오프셋 0x78) 넷뿐, 전부 동작과 무관.
- `cmp rN, #0x78` 10곳 — 야수 쪽은 **0xa10e0 한 곳(읽는 쪽)** 뿐.
- 리터럴 풀에 값 0x78 인 워드 20여 곳 — `re xval 0x78` 이 참조하는 `ldr` 을 하나도 못 찾는다(전부 데이터 표 안의 숫자).
- `#0x1e << 2` / `#0x3c << 1` 같은 계산으로 만드는 자리도 없다.

→ **0x78 은 쓰이지 않는 죽은 갈래로 보인다**(유력). 남은 구멍: 표에서 바이트를 꺼내 `vt44` 로 넘기는 경로라면 상수 검색에 안 잡힌다 — 그 경우를 배제 못 해 "미해결" 로 둔다.

### 7-3. 그래도 알아낸 것 — 0x78 이 무슨 그림인지
`0xa1058` 프레임 표에서 **동작 5 = `12 + [0,1,2,0][min(t,3)]` → 프레임 12·13·14·12** 다.
`0x78` 은 그 중 **프레임 14 하나에 고정**(0xa1200 `movs r4,#0xe`, vt24 보정 없음).
→ 0x78 = **"동작 5 의 세 번째 포즈로 멈춰 서 있기"**. 움직이는 동작이 아니라 정지 포즈 상수다. 웹 이식에서 따로 구현할 필요 없음.

## 8. 경기 상태 `0x20` 진입 경로 — 확정: **들어가는 길이 없다(죽은 상태)**

### 8-1. 새로 알아낸 것 — 상태를 바꾸는 길은 두 가지뿐
1. **직접 예약** `0xbcb48(경기+0x18, n)` — 경기 장면 안 호출지를 전수로 훑었다.
2. **메시지 0** — `0x509a0` 의 메시지 번호 스위치에서 `0` 가지(0x509fc `cmp r2,#0` → `b 0x50c08`):
```
00050a0a: cmp r2, #0 ; bne ; b #0x50c08
00050c08: adds r0,r7,#0 ; adds r0,#0x18
00050c0c: ldr  r1, [sp, #0xec]        ; 인자 = 바꿀 상태 번호 그대로
00050c0e: ldr  r3, =0xbcb49 ; bl 0xca9f8    ; 0xbcb48(경기+0x18, 인자)
```
→ R10 이 "메시지 0(0x13)" 이라고만 적은 것은 **"메시지 0 = 상태 바꾸기, 인자가 곧 상태 번호"** 다. 0x515ca 의 `0xbfbac(경기+0x70, 0, 0x13, 0)` 은 "상태 0x13 으로" 라는 뜻.

### 8-2. 0x20 을 넘기는 곳이 없다 (확정)
- `re xref 0xbcb48` → 206곳, **vtable 칸에 들어간 것 0곳**(전부 리터럴 직접 호출). 즉 위 두 길이 전부다.
- 바이너리 전체에서 `0xbcb49` 리터럴 앞 8줄 안에 `movs r1,#0x20` / `adds r1,#0x20` → **0곳**.
- 바이너리 전체에서 `0xbfbad` 리터럴 앞 7줄 안에 `movs r2,#0x20` → **0곳** (메시지 0 인자 0x20 도 없음).
- 인자가 **계산되는** 예약지도 전부 따라갔다:
  | 자리 | r1 | 결과 |
  |---|---|---|
  | 0x3afb2 (0x1d 갱신) · 0x3aff2 (0x1c 갱신) | `[경기+0x1b6c]` | 그 칸은 `0x1e` 또는 `0xae24c()` 만 들어간다(0x4e770~0x4e792) |
  | 0xae24c | 반환 | `0xd` · `0x17` · `0x18` · `0x1a` · `0` 뿐 (0xae330·0xae334·0xae340·0xae35c·0xae360) |
  | 0x407a8 (0x19 키) | `0xae5f0()` | `0xae5f0: movs r0,#0x17 ; bx lr` → 항상 **0x17** |
  | 0x48bfa | `[경기+0x24]` | 0xbcb48 이 적어 둔 **직전 예약값** 되돌리기 |
  | 0x40528 · 0x40678 · 0x52aac | `[…]` | 모두 위 +0x1b6c 계열 |

### 8-3. 표에는 0x19 의 복사본이 있다 (확정)
갱신 표 `0xd0530`(칸 = 상태 − 7) · 그리기 표 `0xd05a0`(칸 = 상태 − 9) 를 워드로 읽으면:
```
갱신 0xd0530: [0x19] 칸(index 18) = 0x52e9a , [0x20] 칸(index 25) = 0x52e9a   ← 같은 값
   0x52e9a: adds r0,r5,#0 ; bl #0x4b100 ; b #0x52ed0(공통 꼬리)
   빈 번호(0x14·0x15·0x1f 등)는 0x52ed0 (아무것도 안 함)
그리기 0xd05a0: [0x19] 칸(index 16) = 0x5301c , [0x20] 칸(index 23) = 0x5301c  ← 같은 값
   0x5301c: adds r0,r5,#0 ; bl #0x4a384 ; b #0x53032
   빈 번호는 0x53032
```
즉 0x20 은 **빈 칸(기본값) 이 아니라 0x19(경기 끝)와 똑같이 채워진 진짜 칸**이다. 그런데 진입 표 `0xd04bc` 에는 칸이 없고, 아무도 0x20 을 예약하지 않는다.

**판정: 0x20 = 경기 끝(0x19)의 쓰이지 않는 쌍둥이 번호.** 잘려 나간 변형(네트워크/국가대표 등)의 흔적으로 보인다. 웹 이식에서 만들 필요 없다. R10 표의 "들어오는 곳 못 찾음" 은 **"없음"** 으로 닫아도 된다(부정 증거: 위 전수 검색 3종).

## 9. 상태 0x13 의 `+0x199a` 플래그 — 확정

### 9-1. 세우는 식 (0x392ac 전문)
```
000392ac: push {lr}
000392b2: r1 = 경기 + 0x204 ; r3 = [r1]          ; B = 공 객체
000392b6: r3 = [B + 0xab0] ; adds r3,#1 ; bne 0x392ec   ; B+0xab0 != -1 → 끄고 0 반환
000392c2: r3 = [경기 + 0xfd4] ; subs r3,#0x18 ; cmp r3,#2 ; bhi 0x392ec
                                                  ; 결과 코드 ∉ {24,25,26} → 끄고 0 반환
000392ce: r3 = [B + 0xac0] ; r2 = (r3 > 0x6f) ? 1 : 0   ; 111 초과인가
000392e0: 경기+0x199a = r2 ; return r2
000392ec: 경기+0x199a = 0 ; return 0
```

### 9-2. 뜻 (확정)
- `경기+0x204` = **공 객체** (P2 3절과 같은 칸). `공+0xab0` = **담장·폴 맞은 첫 틱**(P2 "state[0x80] = 폴 기둥 맞은 틱 = 공+0xab0") → `== −1` 은 **아직 아무 데도 안 맞았다**.
- `경기+0xfd4` = **타구 결과 코드**(E 2-1a). 웹 `hitDirection.ts:5` 의 `DIRECTED_CODES` 에 24 가 있고 방향 0·1·2 를 더하므로 **24·25·26 = 홈런성 타구(가운데·좌·우)** 다(웹 `swingResult.ts:11` "homeRun(C) 홈런성(24)").
- `공+0xac0` = **낙구 지점까지 거리**를 `min(거리 × 0x109…, 160)` 로 줄인 값(E 2-1b). `> 111` = 160 만점의 **70% 넘게 날아간 타구**.

→ `+0x199a` = **"홈런성이고, 아무것도 안 맞았고, 아주 멀리 가는 타구" 감상 플래그**. 세 조건이 다 맞을 때만 1.

### 9-3. 이 플래그가 바꾸는 것 (기존 노트 연결)
- **상태 0x13**: 공 틱 `+0x1098` 이 `0x406a4(경기)` 문턱을 넘을 때까지 **화면을 붙잡아 둔다**(OK/−5/'5' 로 건너뛰기 가능). 꺼져 있으면 **틱 8** 에 바로 넘어간다 (R10 3절).
- **효과 13 "!"**: 화면에 `!` 연출을 (x, y−52) 에 그린다 (R2 141행).
- **타구음 7** + `경기+0x19a4 = 1`: 0x51408 의 0x515de~0x515f6 에서 같은 판정 `0x392ac` 를 다시 불러서 쓴다(위 4-1 참조). 즉 **"큰 타구 소리 · ! 연출 · 느린 감상" 셋이 한 판정**이다.
- 끄는 곳: 타석 준비(상태 0xf 진입 0x3d978), 그리고 위 세 조건 중 하나라도 틀리면 0x392ac 자신이 끈다.
- 웹판: 없음(연출 계열). 옮긴다면 조건식은 `결과코드 ∈ [24,26] && 폴/담장 미접촉 && 낙구거리스케일 > 111`.

## 10. `ctx+0x24` (0xa77f0 첫 게이트) — 확정, **R8 의 "자동진행(30G)" 해석은 틀렸다**

### 10-1. 게이트 (확정)
```
000a77f0: push {r4,r5,lr}
000a77f2: ldr  r3, [r0, #0x24]     ; ctx+0x24 = 간이 엔진(시뮬) 객체 = scene+0x1780
000a77f6: ldrb r3, [r3]            ; 그 객체의 첫 바이트
000a77fc: cmp  r3, #0 ; beq 0xa7802 ; 0 이 아니면 곧바로 return (기록 없음)
```

### 10-2. 첫 바이트를 쓰는 곳은 딱 둘 (확정)
| 곳 | 값 | 무엇 |
|---|---|---|
| `0xc0e16` (시뮬 초기화 `0xc0dac`) | **0** | `strb r6,[r7]` (r6=0). 경기 시작·CPU 경기·30G 자동진행이 모두 여기를 지난다 |
| `0xc1b8e` (`0xc1b48`) | **1** | `strb r5,[r6]` (r5=1). 반환 1 |

`0xc1b48` 은 P1 2-2 가 이미 푼 **"스스로 강판"** 실행 함수다: `0xac428`(CPU 교체 AI 로 새 투수 고르기) → `0x668cc(전역, 수비팀, 1)` → `engine[0] = 1`.
부르는 곳 두 곳 모두 강판 계열이다 — `0x52c62~0x52c9c`(팝업 코드 0x1b "그만 던지시겠습니까?" 에 예 → 상태 0x21) 와 `0x507f8`(상태 **0x23 = 감독 강판 알림** 의 키 처리 0x50794 → 상태 0x21).

### 10-3. 정정 (확정)
**30G 자동진행은 이 바이트를 세우지 않는다.** 0x3c8da~0x3c95a 를 보면:
```
0003c93c: ldr r4,=0xc0dad ; bl 0xca9fc       ; 시뮬 초기화 → engine[0] = 0
0003c942: r3 = [scene+0x1780] ; adds r3,#0xa0 ; movs r2,#1 ; strb r2,[r3]   ; engine+0xa0 = 1  ← 자동진행 표시는 여기
0003c94a: 0xc0ea8(engine, 0)                  ; engine+0x9f = 0
0003c956: 0xbcb48(scene+0x18, 0x21)
```
→ **자동진행 표시는 `engine+0xa0`** 이고, `engine[0]` 은 0 인 채다. 따라서 R8 1절의 "유력: 자동진행(30G 스킵)이 걸린 뒤로는 기록 없음" 과 R8 8절 머리말의 "모든 기록은 자동진행(ctx+0x24 첫 바이트) 뒤에는 안 들어간다" 는 **바꿔 읽어야 한다**:

> `ctx+0x24` 첫 바이트 = **"사람 투수가 강판되어 남은 경기를 간이 엔진이 끝까지 돌리는 중"**.
> 즉 **투수편(모드 3)에서 내려간 뒤**로는 기록달성이 하나도 안 들어간다. 30G 자동진행은 이 게이트에 안 걸린다(간이 엔진 쪽 지급 지점 0xc15a4·0xc1818 이 살아 있다).

- 웹판: 자동진행·강판 자체가 없다(I 4a). 옮길 때 이 게이트는 "투수편 강판 이후" 조건으로 적어야 한다.

## 11. `state[0x88]` · `state[0x89]` 이름 — 확정 (R8 의 "유력" 해소)

둘 다 **플레이 정산 `0xa8024` 안에서만** 쓰이고, 쓰는 곳은 각각 한 군데다. 둘 다 `state[0x31 + state[0xa]] == 0`(**수비 팀이 사람**) 일 때만 세운다.

### 11-1. `state[0x88]` = **출루 허용** (루에 살아 있는 주자를 남겼다) — 0xa8caa
```
000a8c5c: 주자 i 루프 (수 = 0xa9598(주자관리), 각 = 0xa9564(관리, i))
000a8c66:   r0 = 주자 + 0x78 ; r3 = [r0 + 0x1e]      ; = 주자+0x96 = 아웃 표시 (I 3c)
000a8c6a:   r5 = 0 ; if r3 == 0 → r5 = 1             ; 아웃 안 된 주자가 하나라도 있으면 1
000a8c80: 0xa57f8(ctx, 0x17, r5)                     ; 경기 기록 칸 0x17 에도 같은 값
000a8c8a: r2 = ctx+8 (= state) ; 수비 팀이 사람인가
000a8ca6: if r5 != 0 :
000a8caa:   state[0x88] = 1
```

### 11-2. `state[0x89]` = **피안타** (이번 플레이가 안타였다) — 0xa8d92
```
000a8d5e: r0 = [sp+0x14]           ; = 이번 플레이 "안타" 플래그
                                   ;   (P7 F 절 "…&& !안타([sp+0x14]) …" · Q1 5절 안타 가지 0xa8726 과 같은 칸)
000a8d60: if r0 == 0 → 건너뜀
000a8d64: 0xa57f8(ctx, 0x16, 0)    ; 경기 기록 칸 0x16(연속 무안타 계열) 리셋
000a8d72: 0xa755c(ctx, 2)
000a8d76: 수비 팀이 사람인가
000a8d92: state[0x89] = 1
```

### 11-3. 셋을 나란히 (확정)
| 칸 | 뜻 | 세우는 곳 | 깨는 기록 |
|---|---|---|---|
| `state[0x88]` | **출루 허용** — 정산 뒤 살아 있는 주자가 루에 있음(안타·볼넷·사구·실책 무엇이든) | 0xa8caa | 31 퍼펙트 |
| `state[0x89]` | **피안타** | 0xa8d92 | 30 노히트노런 (+ 31) |
| `state[0x8a]` | **실점**(누계, 99 상한) | 0xa8dd0~0xa8dfa | 29 완봉 (+ 30·31) |
→ 경기 끝 0xa7de8 의 계단 `0x88·0x89·0x8a 모두 0 → 퍼펙트 / 0x89·0x8a 0 → 노히트 / 0x8a 0 → 완봉 / 그 밖 완투` 와 정확히 들어맞는다.
같은 세 칸을 읽어 **경기 중 "노히트 진행 중" 표시**를 고르는 곳도 있다(0xa6490·0xa67b0·0xa701a — 같은 `0x88==0 && 0x89==0 && 0x8a==0` 계단).
